## 3. M1 Spike 得到的事實

這些是 Grill 要面對的現況，不是待討論的選項。數值只列出不涉及隱私的部分。

| 事實 | 對 Grill 的影響 |
| --- | --- |
| 示範路線只有兩條：R01 約 47 公里、R02 約 46 公里 | 路線選單只有兩個選項 |
| 兩條都是**單向的路段**，不是從家出發再回家的完整行程 | 「最晚回程時間」的意義需要重新定義（問題 A1） |
| 兩條路線的典型騎乘時間都在一小時以內 | 一般的出發時間很難碰到日照限制，Demo 情境需要設計（問題 A2） |
| 路線目前只有起點與終點兩個檢查點 | 契約規定休息只能排在中間的檢查點，現在沒有地方可以排休息或加油（問題 A5） |
| 配速在同一條路線上不隨出發時間改變 | 回程餘裕最大的永遠是最早的出發時間（問題 C1） |
| 真實日期沒有路況來源，規則 4 一律是 UNKNOWN | 真實日期的計畫最多是 CONDITIONAL（已定案，問題 D2 只談呈現方式） |
| 加油站資料與氣象署預報要到 M2 才接上 | Prototype 階段這兩項只能用模擬資料 |
| 餘裕係數 0.2 是待驗證的假設 | 介面上的保守估計不能寫成有保證的區間 |

## 4. 待釐清的問題

每個問題附上建議做法，Grill 時一次處理一個。排序依影響程度：前面的問題會改變後面問題的答案。

### 建議的處理順序

C1 → A1 → A2 → B2 → B1 → C2 → A5 → D2 → D1 → E1，其餘依時間處理。

第 1 輪（2026-11-14）已定案：A1、A3、A5、A6、A7、B2、C1、C5、D1。決議見第 7 節；下方表格的「建議」欄是 Grill 之前的建議，與決議不同時以第 7 節為準。

### A. Trip Planner 的使用者操作流程

已定案：欄位有固定路線、日期、出發油量（必填）、最晚回程時間，加上自然語言需求；資訊不足時追問；目錄外的路線回覆不在支援範圍（§2.1 FR1、§9.6）。

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| A1 | 示範路線是單向路段，「最晚回程時間」指的是什麼？ | 改稱「最晚抵達終點的時間」，規則 1 以它和民用暮光終取較早者。來回行程不在 MVP 內 |
| A2 | 一小時以內的路段很難碰到日照限制，Demo 要怎麼呈現規則 1？ | Demo 與題庫刻意包含傍晚出發的情境；不為了情境去串接路線 |
| A3 | 哪些輸入用欄位，哪些用自然語言？ | 會影響規則判定的輸入一律用欄位；自然語言只用來說明休息安排與偏好，Planner 不得用它覆寫欄位 |
| A4 | 候選出發時間由誰決定？ | 騎士填「最早可出發時間」，系統每 30 分鐘產生候選，到無法在期限內抵達為止 |
| A5 | 路線只有起訖兩個檢查點，休息與加油要排在哪裡？ | M2 接上加油站資料時，為每條路線人工加上 1–2 個中途檢查點；在那之前 Prototype 用模擬的檢查點 |
| A6 | 出發油量用什麼單位輸入？ | 用油箱的百分比，公升數由 Rider Profile 的油箱容量換算 |
| A7 | 日期超出預報涵蓋期間時，介面要擋下來還是照常規劃？ | 照常規劃並把規則 3 標成 UNKNOWN，這正好展示資料缺失的處理 |

### B. 結構化的 Plan Schema

已定案：每條規則的結果是 PASS／FAIL／UNKNOWN；計畫狀態是 FEASIBLE／CONDITIONAL／INFEASIBLE；一次 ETA 計算有一個 `plan_id`；回答中的數字都要來自工具輸出（§4.2、§5、NFR1）。Smoke Test 用的輸出格式只是測試用的，不是 Plan Schema。

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| B1 | 一次規劃的結果要包含哪些候選？ | 包含全部評估過的候選：每個候選有出發時間、`plan_id`、逐條規則結果與計畫狀態；另外標出被選中的候選 |
| B2 | 計畫裡的數字由誰填？ | 由主程式從工具輸出填入，Planner 只產生工具呼叫與說明文字。這樣規則 5 只需要檢查說明文字裡的數字 |
| B3 | 逐條規則結果要記錄哪些欄位？ | 規則編號、結果、原因代碼、引用的工具輸出、資料來源與取得時間、是否為模擬資料 |
| B4 | UNKNOWN 的原因要不要列舉成固定的代碼？ | 要。例如沒有資料來源、超出涵蓋期間、外部服務失敗、缺少必要輸入 |
| B5 | 油量計畫怎麼表示？ | 每個檢查點的剩餘油量、哪些加油站安排加滿，以及安全保留油量 |
| B6 | E2 的另外兩組（沒有 Validator）要輸出同一份 Schema 嗎？ | 輸出同一份 Schema 的共同子集，計畫狀態由 LLM 自行宣告，並標示不是 Validator 的結果 |

### C. Validator 的三值狀態與重新規劃

已定案：三值結果與三種計畫狀態；先比狀態再比回程餘裕；INFEASIBLE 不作為建議；候選全部 INFEASIBLE 才重新規劃；重試有次數上限（§4.2、§8）。

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| C1 | 同狀態下比回程餘裕，最早出發的候選永遠勝出，候選搜尋變得沒有意義。要怎麼選？ | 騎士填「偏好的出發時間」；在同狀態、餘裕不低於門檻的候選中，選最接近偏好時間的。排序仍是先比狀態 |
| C2 | 路線固定時，重新規劃可以改什麼？ | 只能改出發時間的範圍與加油安排。換到另一條示範路線只出現在不可行報告的替代方案裡，不自動執行 |
| C3 | 重試次數上限設多少？ | 2 次 |
| C4 | 規則 3 的「日照限制最緊的最後一段」在單向路線上怎麼界定？ | 以最後一個路段為準；若要放寬成最後幾段，由 Grill 定一個固定的數量 |
| C5 | 騎士可以自己確認路況來消除規則 4 的 UNKNOWN 嗎？ | 不可以。Validator 只依資料判定；介面把「出發前自行確認路況」列為待辦事項 |
| C6 | 暮光終是 UNKNOWN 時，回程餘裕只用騎士的期限計算，這個候選能和暮光終已知的候選一起排序嗎？ | 可以，因為狀態已經先區分了 CONDITIONAL 與 FEASIBLE |

### D. UI 的三個畫面與 UNKNOWN 的呈現

已定案：Trip Planner、Trip Result、Validation & Replanning 三個畫面；Validator 的三值狀態與來源證據以獨立區塊呈現；保守估計不稱為 P90；高降雨機率提醒不稱為警特報；模擬資料要標示（§9.6、NFR5）。

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| D1 | 三個畫面是三個獨立頁面，還是同一頁的三個區塊？ | 同一頁：上方是輸入，下方以分頁切換 Trip Result 與 Validation & Replanning |
| D2 | CONDITIONAL 和 FEASIBLE 在畫面上怎麼區分？ | 狀態標籤加上「出發前要自行確認的事項」清單；清單逐條對應 UNKNOWN 的規則 |
| D3 | 一條 UNKNOWN 的規則要顯示什麼？ | 不知道的是什麼、為什麼不知道（原因代碼的說明）、嘗試過的資料來源、騎士該怎麼確認 |
| D4 | 候選要全部顯示，還是只顯示被選中的？ | 預設顯示被選中的候選，其餘收在可展開的表格 |
| D5 | 重新規劃的過程要顯示到什麼程度？ | 顯示每一輪改了什麼與結果，不顯示 Planner 的內部文字 |
| D6 | 無可行解的畫面要有什麼？ | 違反的規則、各候選失敗的原因、替代方案 |
| D7 | 來源證據區塊要有什麼？ | 每個資料來源的名稱、真實或模擬、取得時間、涵蓋範圍 |
| D8 | 對話放在哪裡？ | 只用在一開始的自然語言需求與追問；結果以結構化區塊呈現，不放進對話文字 |

### E. Streamlit 的實作限制

以下事實由查證用的子代理在 2026-11-14 對照 Streamlit 官方文件（docs.streamlit.io，版本 1.67.0，2026-11-05 發布）整理。這是子代理的報告，我沒有逐條重新核對；Prototype 開始前若有疑問，以官方文件為準。

| 事實 | 對 Prototype 的意義 |
| --- | --- |
| 每次互動預設會重新執行整份腳本；跨互動的狀態放在 `st.session_state`，瀏覽器重新整理後會清空 | 規劃結果要存在 session state；不能假設重新整理後結果還在 |
| `st.form` 把輸入集中到送出時才處理；表單內不能放一般按鈕與下載按鈕，也不能巢狀 | Trip Planner 的輸入適合用一個表單；「重新規劃」與下載按鈕要放在表單外 |
| `required=True` 是 1.67.0 的新參數，只在瀏覽器端擋下送出，文件說明可以被繞過 | 出發油量是必填，送出後程式仍要再檢查一次 |
| 分頁（`st.tabs`）、可展開區塊（`st.expander`）、欄（`st.columns`）、對話框（`st.dialog`）都有；可展開區塊不能巢狀，欄最多巢狀一層，一次執行只能開一個對話框 | 同一頁加分頁的結構做得出來 |
| 狀態標籤有原生的 `st.badge`，顏色有紅、橘、黃、藍、綠、紫、灰 | PASS／FAIL／UNKNOWN 與計畫狀態可以用標籤呈現 |
| `st.dataframe` 是唯讀表格，可排序、可選取列；`st.metric` 是數值卡片 | 候選清單與逐條規則結果可以用表格，並支援點選一列看細節 |
| 對話元件有 `st.chat_input` 與 `st.chat_message` | 追問可以用對話元件 |
| `st.spinner`、`st.status`、`st.progress` 可顯示進度；官方文件沒有說明單一長時間呼叫的真實進度百分比 | 規劃期間顯示分步驟的狀態文字，不顯示百分比 |
| 只有 `help=` 的提示文字會在滑鼠停留時出現；`st.popover` 是點擊才開 | 重要資訊不能只放在滑鼠停留時才看得到的地方 |
| 沒有原生的拖曳排序；沒有伺服器主動推送，只能定時重跑；`st.map` 只能畫點、不回傳事件 | Prototype 不使用這些互動 |
| 多頁應用切換頁面時，元件的狀態預設會重置 | 支持「同一頁加分頁」的做法 |

子代理沒有查證的事項：分頁與可展開區塊的延遲載入參數是哪一版加入的。

| 編號 | 問題 | 建議 |
| --- | --- | --- |
| E1 | HTML Prototype 可以使用哪些元件，才不會做出 Streamlit 做不出來的東西？ | 只用：表單欄位、按鈕、分頁、可展開區塊、表格、數值卡片、狀態標籤、對話訊息、進度指示 |
| E2 | 哪些互動要明確排除？ | 拖曳、只在滑鼠停留時出現的資訊、表格內直接編輯、畫面即時更新、自訂的地圖互動 |
| E3 | 規劃執行期間畫面怎麼處理？ | 同步執行並顯示進度；不做背景執行與逐字串流 |
| E4 | 改了輸入之後，結果要自動重算還是按鈕觸發？ | 按鈕觸發；輸入改變後把舊結果標成過期 |
| E5 | Demo 與影片錄製時若外部服務不可用怎麼辦？ | 提供使用資料快照的模式，畫面上明確標示為快照或模擬資料 |

## 5. 固定用語

Grill、Prototype 與 Spec 都使用同一套用語，避免混用。

| 用語 | 意義 |
| --- | --- |
| PASS／FAIL／UNKNOWN | 單一規則的結果 |
| FEASIBLE／CONDITIONAL／INFEASIBLE | 整份計畫的狀態 |
| 典型估計（`ETA_typ`） | 依配速表算出的抵達時間 |
| 保守估計（`ETA_safe`） | 典型估計加上安全餘裕；不是 P90，沒有覆蓋率保證 |
| 高降雨機率提醒 | 降雨機率達到專題自訂門檻；不是氣象署的警特報，也不表示降雨強度 |
| 安全保留油量 | 任何檢查點都不得低於的油量，暫定為油箱容量的 20% |
| 檢查點 | 路線上的起點、終點、加油站或途經點，位置以完成的路段數表示 |
| 候選 | 一個出發時間與它的 ETA、規則結果與狀態 |
| 模擬資料 | 人工編寫的測試資料，必須帶來源標記並在畫面上標示 |

九題全部定案，不再重新審查。

| 題號 | 對應 | 決議 |
| --- | --- | --- |
| Q1 | A1 | 一次規劃是一條固定的單向路線，從頭騎到尾。期限統一稱「最晚抵達終點時間」。規則 1 使用它與民用暮光終的較早者 |

| Q4 | A3 | 影響驗證的主要條件使用表單。自然語言可以補充休息與偏好，但會影響 ETA 的休息安排必須轉成結構化資料。與表單衝突時以表單為準，並提示使用者 |
| Q5 | A5 | M2 為每條路線人工加入 1–2 個**真實**的中途檢查點，必須落在路段邊界並有來源。Prototype 可以使用明確標記為 simulated 的模擬檢查點，不得當成真實站點 |
| Q6 | A6 | 出發油量以百分比（0–100%）輸入，由工具依 Rider Profile 換算成公升 |
| Q7 | A7 | 日期超出預報期間時繼續規劃，天氣規則為 UNKNOWN。其他規則若有 FAIL，整份計畫仍是 INFEASIBLE |
| Q8 | C5 | 使用者自行確認路況不能把 UNKNOWN 改為 PASS；介面顯示為待確認事項 |
| Q9 | D1 | 單頁設計：Trip Planner 的輸入固定呈現，Trip Result 與 Validation & Replanning 以分頁切換。Streamlit 的可實作性在 Prototype 階段確認 |

十四題全部定案。
