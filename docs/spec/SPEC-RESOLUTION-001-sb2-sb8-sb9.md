## 1. SB-2：停等寬放

### 1.1 各種時間的定義

| 名稱 | 定義 | 由誰決定 | 算進哪裡 |
| --- | --- | --- | --- |
| 停等事件 | 連續的「停止」步合成一個事件，長度是這些步的時間總和。停止步的判定不變：低於 3 km/h，或記錄中斷超過 10 秒且位移不到 50 m | `ingest` | — |
| 疑似 GPS 假停留 | 長度**小於 3 秒**的停等事件。多半是位置重複一筆造成的；程式無法逐一證實，所以稱為「疑似」 | `ingest` | **移動時間**（不加里程） |
| 移動時間 | 行進的時間加上疑似 GPS 假停留的時間 | `ingest` | 配速表的速度；E1 的移動時間比較 |
| 真正的短停留 | 長度 **3 秒以上、不到 180 秒**的停等事件：紅燈、車流、路口 | `ingest` | **非計畫性停等寬放**的依據 |
| 長停留 | 180 秒以上的停等事件：休息、加油、拍照 | `ingest` | 不進配速表，不進寬放，不進誤差。規劃時沒有安排的長停留，ETA 不會包含 |
| 非計畫性停等寬放 | 規劃時加在每個路段典型時間上的短停留估計 | `pace`，由配速行程的短停留算出 | `ETA_typ` |
| 安排的休息與加油 | 騎士當次指定，或依 Rider Profile 排入的休息；加油停留的長度來自 Rider Profile | 表單、Planner、主程式 | `ETA_typ`，以 `breaks` 表示；不乘餘裕係數 |
| 安全餘裕 | 餘裕係數乘上到這一點為止的典型騎乘時間 | `pace` | 只加在 `ETA_safe` |

兩個門檻的理由：

- **3 秒**。配速行程的停等事件中，1 秒的有 2,234 次；長度不超過 2 秒、而且前後兩步都快於 20 km/h 的有 2,233 次。行進中不可能停 1–2 秒。以 3 秒為界時，假停留共 2,491 次，占現行移動時間的 3.5%。
- **180 秒**。和檢查 C2 相同，當時在執行前寫定。配速行程中 180 秒以上的停留只有 4 次，長時間的休息多半落在兩個檔案之間。

把 1–2 秒的事件算成移動時間或短停留，騎乘時間的總和不變，只影響它由速度還是由寬放來估計。所以這個門檻不會改變整趟的估計，只改變 E1「移動時間」的定義。

### 1.2 算式

```text
每個路段 s（類別 c）：
  typ_mov(s)   = length(s) ÷ speed(c)                       典型移動時間
  stop_allow(s) = stop_ratio(c) × typ_mov(s)                非計畫性停等寬放
  typ_ride(s)  = typ_mov(s) + stop_allow(s)                 典型騎乘時間

到第 k 段終點：
  RIDE(k)      = Σ(s ≤ k) typ_ride(s)
  BREAK(k)     = 在第 k 段終點之前已排入的休息與加油時間總和
  ETA_typ(k)   = 出發時間 + RIDE(k) + BREAK(k)
  ETA_safe(k)  = ETA_typ(k) + margin_coeff × RIDE(k)

配速表（只用配速行程中可計時的路段）：
  speed(c)      = 各路段 length ÷ moving_time 的未加權中位數          （不變）
  stop_ratio(c) = Σ short_stop_time ÷ Σ moving_time                  （新增；合併計算）
```

不重複計算的四條規則：

1. 疑似 GPS 假停留只進移動時間，不進寬放。
2. 短停留只進寬放，不進速度。
3. 長停留、安排的休息與加油只以 `breaks` 進入 `ETA_typ`；它們不乘餘裕係數，也不進寬放。
4. 餘裕係數在加入寬放之後才決定，所以它只反映寬放沒有解釋的差距。

**餘裕係數的決定規則。** 對配速行程做留一趟：每一趟的實際騎乘時間（移動加短停留）和預測的 `RIDE` 比較。`margin_coeff` 取 0.05 的倍數中最小的一個，使得「實際騎乘時間 ≤ 預測 × (1 + margin_coeff)」除了最多兩趟之外都成立；下限 0.05。可用的行程（計入的折數，見下）少於 8 時用預設的 0.20。它是描述性的設定值，不是 P90，沒有覆蓋率的保證。

留一趟的程序（聚焦審查後寫完整）：(1) 每一折以其餘行程的 `curvature_deg_per_km` 依同一條三分位規則重算分級門檻並重新分類；這只用契約 1 的欄位，不需要重跑 `ingest`。(2) 被拿掉的那一趟有任何類別算不出配速時，這一折不計入；它沒有預測，不參與比較。(3)「可用的行程」指計入的折數，少於 8 時用預設的 0.20。

**分級門檻的規則（第二輪聚焦審查後補上）。** 上面的「三分位規則」：取表頭 `trip_ids` 的行程中品質為 `ok` 的路段的 `curvature_deg_per_km`，排序後取三分之一與三分之二位置的值，各四捨五入到 5 度／km（沿用 M1 Spike 與檢查 C2 的規則）。每次建立配速表都重算，`research-` 與 `user-` 相同；結果寫在表頭的 `category_scheme`。留一趟的每一折用同一條規則，母體是那一折其餘的行程。定義處是 DESIGN §6.1。這一項已核准（2026-11-15，Q-4）。

**餘裕係數和配速表綁在一起（裁決後修正）。** 每次建立配速表時，以同一批行程依上面的規則算出 `margin_coeff`，寫在配速表的表頭。`speed`、`stop_ratio` 與 `margin_coeff` 因此永遠來自同一批資料，不會出現更新了速度與停等比例、卻沿用舊餘裕係數的情形。計入的折數少於 8 時 `margin_coeff` 是預設的 0.20，介面要說明這是預設值，不是由資料得出的。資料算出來的值也可能剛好是 0.20（試算就是），所以表頭另以 `margin_basis`（`loo_rule` 或 `default`）標示來源；這個欄位已核准（2026-11-15，O-3；1.4）。

**研究用與使用者的 Profile 分開（裁決後修正）。** `pace_version` 分兩種：`research-` 開頭的是研究凍結的配速表，由凍結用的腳本建立；E1 與 E2 只讀凍結清單指定的那一個版本。`user-` 開頭的是介面上傳歷史 GPX 後重建的配速表，不影響研究用的版本。**兩種都不改寫**（第二輪聚焦審查後寫明）：每次建立都是新的版本、新的檔案，既有的檔案不修改；編號在兩種開頭各自遞增。「`user-` 版本也不改寫」已核准（2026-11-15，Q-4）：使用者每次更新 Profile 可以重新計算分級門檻與配速參數，但一定產生新的版本，不覆寫舊的版本；E1／E2 的凍結 Profile 完全獨立，不會被任何 Profile 更新修改；版本可以由契約 3 既有的表頭與類別欄位追溯，不需要新增欄位（DESIGN §6.1）。產品的規劃用 `built_at` 最晚的 `user-` 版本；沒有時用凍結清單指定的 `research-` 版本。`pace_version` 的格式是 `research-` 或 `user-` 加兩位以上的數字，依建立順序遞增；「最新」依表頭的 `built_at`（格式已核准，2026-11-15，O-3；1.4）。`pace_version` 是契約 3 既有的主鍵，沒有新增欄位。兩種配速表用同一個契約、同一個建立程序與同一條餘裕係數規則，只差在開頭與有沒有凍結清單：`research-` 的版本另外由凍結清單記錄 SHA-256 並在執行前核對，`user-` 沒有凍結清單。契約 4 只記版本字串，單看契約資料無法確認一份 ETA 用的是哪一份配速表檔案；這一點寫入限制（DESIGN §12）。

**研究用配速表的完整性（聚焦審查後補上）。** 凍結清單除了 `pace_version`，另記研究用配速表檔案與它所用的衍生路段表的 SHA-256；E1、E2 的腳本執行前核對，不符就停止。凍結用的腳本遇到既有的 `research-` 版本時報錯，不覆寫。

### 1.3 試算（16 趟配速行程，留一趟）

腳本是 `experiments/cr01_checks/data_sb2_stop_allowance.py`，在現行 `ingest` 之上模擬假停留的修正，沒有修改 `src/`。正式的參數要由實作後的程式以同樣的程序重算。定義、候選模型與選擇規則都在執行前寫進腳本。

| 項目 | 數值 |
| --- | --- |
| 疑似 GPS 假停留（不到 3 秒） | 2,491 次，占現行移動時間的 3.5% |
| 短停留（3–180 秒） | 326 次（全部路段的事件數） |
| 短停留 ÷ 移動時間：全部／C1／C2／C3 | 13.5%／14.4%／23.4%／4.8% |
| 各趟的比例：第一四分位／中位數／第三四分位 | 9.0%／12.4%／21.0% |
| 移動時間的誤差（修正假停留之後；不含寬放） | MAPE 8.3%，平均帶符號誤差 −4.5% |

| 模型 | 騎乘時間的 MAPE | 平均帶符號誤差 | 偏樂觀的趟數 |
| --- | --- | --- | --- |
| 不加寬放 | 16.0% | −16.0% | ≥14 |
| M1 全部類別共用一個比例 | 10.2% | −4.7% | 9 |
| **M2 每個類別一個比例** | **9.5%** | **−3.7%** | 10 |

| 基準 B1：單一「騎乘速度」（里程 ÷ 騎乘時間） | 17.2% | +5.0% | 10 |

- 事前寫定的選擇規則是「MAPE 最低；相差 0.5 個百分點以內時取最簡單的」。結果是 **M2**。
- 三個模型套用餘裕係數的規則都得到 **0.20**，和目前的暫定值相同；實際騎乘時間落在保守估計內的趟數是 ≥14。
- 留一趟每一折都重算分級門檻。實際計入的折數是 ≥14：16 趟中有 <3 趟因為被拿掉時有類別算不出配速，沒有計入（彙總檔遮蔽了小的趟數）。
- 要注意的事：比例由不多於 326 次短停留決定。326 是全部路段的短停留事件數，比例只用可計時的路段，確切的次數沒有另外算；分到三個類別之後更少。C2 的 23.4% 和 C3 的 4.8% 相差很大，可能受少數幾次停留影響。M2 比 M1 只好 0.7 個百分點。分級門檻不穩定（R25）也會帶到 `stop_ratio`。
- 沒有使用檢查 C2 的 19.1% 作為係數；它含疑似 GPS 假停留，而且是誤差，不是比例。

**裁決：採 M2。** 每個 C1／C2／C3 類別各一個 `stop_ratio`。M1 不採用。

### 1.4 契約的最小變更

契約 3、4 之外，**契約 1 也必須加一個欄位**：`pace` 只讀契約 1，現行的 `stopped_time_s` 把疑似 GPS 假停留、短停留與長停留混在一起，算不出寬放。第 8 節的裁決批准的是三個新增欄位：`short_stop_time_s`、`stop_ratio`、`stop_allow_s`。契約 3 表頭的 `margin_coeff`、`margin_basis` 與 `pace_version` 的格式是由裁決推導的，**已在 2026-11-15 另外核准**（O-3；[lead 的處置](../cr/CR-01-appendix/lead_dispositions_resolution.md)第 5.3 節）。`pace_version` 是契約 3 既有的主鍵，沒有新增欄位。

| 契約 | 欄位 | 變更 |
| --- | --- | --- |
| 1 衍生路段表 | `moving_time_s` | 定義改為「行進時間加上不到 3 秒的停等事件」。型別不變 |
| 1 | `stopped_time_s` | 定義改為「3 秒以上的停等事件的時間總和」。型別不變 |
| 1 | `short_stop_time_s`（新增） | number，≥ 0：其中 3 秒以上、不到 180 秒的部分。恆有 `short_stop_time_s ≤ stopped_time_s` |
| 1 | `ingest_version` | 換新值。兩個門檻（3 秒、180 秒）是 `ingest` 的參數，由版本追溯 |
| 3 配速表（類別紀錄） | `stop_ratio`（新增） | number 或 null，≥ 0。`speed_kmh` 是 null 時它也是 null；其他情形必有值，可以是 0 |
| 3（表頭） | `pace_version`（既有的主鍵，沒有新增欄位；格式由裁決的第 5 點推導，**已核准**，O-3） | 換新值。格式是 `research-` 或 `user-` 加兩位以上的數字，依建立順序遞增；「最新」依表頭的 `built_at`。`method` 不變 |
| 3（表頭） | `margin_coeff`（新增；由裁決的第 5 點推導，**已核准**，O-3） | number；0.05 的倍數，≥ 0.05。`margin_basis = loo_rule` 時，以表頭 `trip_ids` 的行程做留一趟，依 1.2 的規則與程序算出；`margin_basis = default` 時固定為 0.20。和同一份配速表的 `speed_kmh`、`stop_ratio` 用同一批行程、同一個 `ingest_version` |
| 3（表頭） | `margin_basis`（新增；由裁決的第 5 點推導，**已核准**，O-3） | enum：`loo_rule`（依 1.2 的留一趟規則由資料算出）或 `default`（用預設的 0.20）。計入的折數少於 8 時是 `default`，否則是 `loo_rule`。介面在 `default` 時顯示固定說明；沒有它，介面無法知道餘裕係數是不是預設值 |
| 4 ETA 輸出（路段列） | `stop_allow_s`（新增） | number 或 null，≥ 0。狀態是 `unknown` 時為 null |
| 4（表頭） | `margin_coeff` | 欄位不變；下限改為 0.05，和契約 3 一致。保留實際採用的值，供追溯：值必須等於所用配速表（`pace_version`）表頭的 `margin_coeff`（已核准，O-3） |

契約 3 的「表頭的 `margin_coeff` 等於依規則重算的值」由產生者的測試（SB2-T9）檢查，不由契約驗證程式檢查：驗證程式不計算配速或 ETA。

契約 3 另有兩條不變條件（第二輪聚焦審查後補上）：`margin_basis` 只有 `loo_rule` 與 `default` 兩個值，是 `default` 時 `margin_coeff` 必為 0.20，是 `loo_rule` 時 `margin_coeff` 是 0.05 的倍數且不小於 0.05；`pace_version` 符合樣式（`research-` 或 `user-` 加兩位以上的數字）。表頭沒有計入的折數，所以 `margin_basis` 是否正確（計入的折數少於 8 才是 `default`）由產生者的測試檢查，不由契約驗證程式檢查。既有測試 fixture 中不符合新樣式的 `pace_version`，實作時要改名。

Plan Schema（SPEC-001）不新增欄位：介面不顯示寬放的秒數，只在抵達時間旁加一句固定文字（依裁決修正）：「抵達時間已包含路上短暫停等（紅燈、車流）的估計，以及排入的休息與加油；不包含沒有安排的長時間停留。」

### 1.5 E1 的兩種比較

| 比較 | 預測 | 實際 | 基準 | 用途 |
| --- | --- | --- | --- | --- |
| 移動時間（保留） | Σ `typ_mov` | Σ `moving_time_s` | B0：單一速度，全部可計時路段速度的不加權中位數（和檢查 C2、試算一致） | 回答個人配速表本身準不準 |
| 記錄範圍內的騎乘時間誤差（新增） | Σ `typ_ride` | Σ（`moving_time_s` ＋ `short_stop_time_s`） | B1：單一騎乘速度（里程 ÷ 騎乘時間）。另加一列對照：單一中位數速度 ×（1 ＋全部類別共用的停等比例），和個人配速表只差在有沒有分類 | 回答不含長停留的騎乘時間準不準 |

- 兩者都只算可計時的路段，以「趟」為單位報告 MAE、MAPE 與平均帶符號誤差，並依類別分層。
- 「整趟」在 E1 指的是一個 GPX 檔修剪後的記錄範圍內，移動時間加短停留的總和。它**不是門到門的總歷時**：不含長停留，也不含兩個檔案之間的時間。報告與簡報都要寫明這個定義。
- 騎乘時間誤差另報告「實際騎乘時間 ≤ 預測 × (1 + margin_coeff)」的趟數，只作描述。
- 長停留不在任何一種比較裡。門到門的總歷時不評估。
- `speed`、`stop_ratio`、`margin_coeff`、分級門檻都只由 16 趟配速行程決定，在讀取保留行程之前凍結。4 趟保留行程由隔離的評估腳本在凍結之後讀取，產生一份封存的衍生資料，供兩個用途：E2 真實行程題的 Oracle 答案與 E1 的最後報告；之後不再讀原始檔。保留行程不用來調整。12/5 的凍結項目包含「E1 的分析計畫已寫定並記錄日期」。
- 凍結之前，`ingest` 與配速表的重建只處理配速行程：保留行程與被排除的行程的檔案不開啟，衍生路段表中沒有 `trip_role = holdout` 的列。保留行程的列在分析方法與模型設定凍結之後，由隔離的評估腳本以凍結的 `ingest_version` 產生。介面上傳歷史 GPX 時，內容和保留行程或被排除的行程相同的檔案以內容去重複略過，不重新歸為配速行程。
- 假設 H1（山路的代理路段上，移動時間的比較）以 16 趟配速行程的留一趟判定；這是開發數字，不是事前預測。4 趟保留行程的結果只作描述，不用來判定假設。移動時間的定義在 2026-11-15 依配速行程的分布修訂（3 秒的門檻）。
- 騎乘時間的對照列（單一中位數速度加共用的停等比例）是聚焦審查後加的，1.3 的試算沒有算這一列。

## 2. SB-8：SPEC-001 7.11 的待定項目

八項的推薦值都是設定常數，寫在一個設定檔，定案後不依測試結果調整。都不需要新的 GIS 特徵、圖資下載或額外的 Agent。

### 2.1 路線快照的產生、重用與失效（7.11 第 3 項）

| 情形 | 推薦 |
| --- | --- |
| 產生 | 一般模式：先算 `request_key`。沒有可重用的快照時呼叫路線引擎（來回行程兩次），再做道路屬性查詢（2.4）。每個方向都要通過三項檢查才存檔：回應沒有警告、國道檢查通過、起點、終點與每一個中間位置的偏移都在門檻內，而且中間位置的順序相符（2.5）。任何一項沒通過就不存檔，回傳路線錯誤 |
| 不可變（修正 A） | 快照檔寫入一次之後不再修改，程式也不刪除。快照由正規化後的內容產生代號：重新取得後內容完全相同就沿用既有的檔案，不寫入、不修改；內容不同就建立**新的**快照、新的代號，不覆寫舊的。以既有的代號寫入不同的內容時報錯。E2 與 Demo 凍結的快照因此不會被覆寫（2026-11-15，Q-3 第 1 項的裁決） |
| 重用 | 一般模式：有 `request_key` 相同、`freeway_check_method` 和現行的檢查方法相同、取得時間在 **30 天**內的快照時，用其中最新的一個，不呼叫引擎 |
| 失效 | (a) `request_key` 不同；(b) 超過 30 天；(c) `freeway_check_method` 不同（國道檢查的方法或門檻改過時，這個字串跟著改）。失效只表示一般模式不再重用，檔案原樣保留 |
| 重新取得 | 失效後重新呼叫引擎。內容不同時存成新的快照；內容完全相同時沿用既有的檔案，它的取得時間不更新。舊檔不動。後果：同一條路超過 30 天之後，一般模式每次規劃都會重新向路線引擎取得；內容沒有變時不產生新檔。這是 MVP 的已知限制；不偽造或覆寫取得時間，也不為此新增複雜的快取架構（2026-11-15 的裁決，處置第 9.10 節） |
| 引擎失敗 | 回傳 `routing_unavailable`。一般模式不改用已失效的快照；騎士可以切到 Snapshot Mode |
| Snapshot Mode | 只讀已保存的快照，不呼叫路線引擎，不看 30 天的期限。一般的 Snapshot Mode（沒有指定凍結清單）：用 `request_key` 相同、`freeway_check_method` 和現行方法相同的已保存快照中，取得時間最晚的一個；沒有時回傳 `snapshot_missing`。嚴格模式（執行時指定了凍結清單：E2 的 Runner 與凍結的 Demo；這個觸發方式是 lead 寫定）：只採用清單指定的 `snapshot_id`，並核對檔案的 SHA-256；凍結清單沒有對應的 `request_key` 或 `snapshot_id`、檔案不存在或雜湊不符時停止執行，不回退到任何其他快照（沒有對應的項目時停止是 2026-11-15 的裁決，處置第 9.9 節）。兩種模式下，`freeway_check_method` 和現行方法不同的快照都不採用；嚴格模式下遇到這種情形同樣停止（2026-11-15，Q-3 第 6 項的裁決） |
| E2 與 Demo 的凍結 | 凍結清單列出每個快照的 `snapshot_id` 與檔案的 SHA-256。E2 的題目以 `route_id` 指定快照。E2 的 Runner 與凍結的 Demo 以嚴格模式執行（上一列），不經過一般的選擇。凍結清單中的快照在凍結時以現行方法檢查過；檢查方法在 E2 凍結之後不得更改 |

Q-3 的裁決（2026-11-15；[lead 的處置](../cr/CR-01-appendix/lead_dispositions_resolution.md)第 8.1、8.6 節）：快照代號取自正規化後的內容，內容相同就重用，內容不同就建立新的快照、不覆寫（第 1 項，有條件批准）；Snapshot Mode 分成一般模式與嚴格模式，凍結清單記錄檔案的 SHA-256（第 6 項，修改）。雜湊不含 `snapshot_id` 與各方向的取得時間、「指定了凍結清單就是嚴格模式」是 lead 寫定。先前「每一次成功取得都是新的快照、新的代號」與「Snapshot Mode 先查凍結清單，沒有時用最新的一個」的寫法作廢。裁決之前的原文在 [q3_derived_details.md](../cr/CR-01-appendix/q3_derived_details.md)。

理由：公開伺服器只能低頻使用；圖資每天更新，但山區公路很少變動；快照的圖資日期顯示在來源證據，過期與否看得到。30 天是推薦值，替代選項是 7 天（較新，請求較多）。

不另外建立版本管理：不可變靠「代號取自內容、檔案只寫一次」達成，沒有索引檔，也沒有版本號。

測試：SB8-T1 同一請求第二次規劃不呼叫引擎；SB8-T2 以 31 天前取得的快照測試，一般模式重新取得（內容不同時存成新檔，內容相同時沿用舊檔），舊檔的內容不變，Snapshot Mode 仍然可以使用舊檔；SB8-T3 引擎失敗且只有過期快照時，一般模式回傳 `routing_unavailable`；SB8-T4 回程檢查沒通過時，去程也不存檔；SB8-T4a 以既有的代號寫入不同的內容會報錯，檔案不變；SB8-T4b 凍結清單的雜湊和檔案不符時 Runner 停止。Q-3 的裁決之後增加 Q3-T1 至 T6（快照的重用、不覆寫、正規化、已保存結果的指向）與 Q3-T22 至 T25（Snapshot Mode 的兩種模式），見處置第 8.1、8.6 節；SPEC-001 第 9 節的 S53–S58、S74–S77。Q-3 後續的裁決之後增加 Q3-T34（凍結清單沒有對應的項目時停止；處置第 9.9 節；SPEC-001 第 9 節的 S86）。

### 2.2 ID 與快取鍵的關係（7.11 第 1、4 項；SB-1）

| 名稱 | 組成 | 用途 |
| --- | --- | --- |
| `request_key` | 正規化 JSON 的 SHA-256：`trip_type`、起點、目的地、途經點（含 `entry_ref_id`，依順序）、`routing_params`。每個地點以「代號加指紋」表示：指紋是該地標座標定義的 SHA-256 前 16 碼，座標先正規化為小數六位 | 找快照用的鍵。不顯示；鍵裡沒有座標本身 |
| `snapshot_id` | `SN-` 加正規化後的快照內容的 SHA-256 前 10 碼。雜湊的範圍不含 `snapshot_id` 本身與各方向的取得時間（`fetched_at`；lead 寫定） | 快照內容的代號。內容完全相同就是同一個代號，沿用既有的檔案；內容不同才是新的代號 |
| `route_id`（路線引擎） | `RS-` 加同一組 10 碼 | 和快照一對一；新的快照有新的 `route_id`。已保存的結果繼續指向它當時使用的 `route_id` 與 `snapshot_id` |
| `route_id`（目標 GPX） | `RG-` 加「檔案內容的 SHA-256 與 `trip_type` 合併後」的 SHA-256 前 10 碼。合併的寫法：檔案內容 SHA-256 的十六進位字串、一個冒號、`trip_type` 的值，依序相接；來回行程再接一個冒號與實際採用的折返位置（距起點的累計公尺，取整數；不論它是自動判定還是騎士指定的），單向行程沒有這一段；相接後取 SHA-256。折返位置的部分依 2026-11-15 的裁決（處置第 9.1 節） | 沒有快照。同一個檔案的單向與來回是兩條路線；相同的幾何、相同的有效折返點得到相同的 `route_id`，不同的折返點得到不同的 `route_id` |
| `route_id`（示範路線） | `R01`、`R02`，不變 | fixture |
| `checkpoint_id` | `<route_id>-CP` 加兩到三位數字，依路線順序由 01 起編 | 不變的規則，放寬長度 |

- Q-3 第 1 項的裁決（2026-11-15，有條件批准；處置第 8.1 節）：`SN-`／`RS-`／`RG-` 與 `checkpoint_id` 的格式接受；內容完全相同就重用，內容不同就建立新的快照，不覆寫舊的；已保存的結果繼續指向原來的快照，不能默默替換。雜湊的範圍不含 `snapshot_id` 與各方向的取得時間是 lead 寫定：取得時間每次都不同，含在內就永遠不會「內容完全相同」。這個設計已由 2026-11-15 的裁決保留（處置第 9.10 節）。
- 一個 `request_key` 可以對應多個不同時間的快照；一個快照只對應一個 `route_id`。
- `request_key` 不用整份詞彙表的版本（聚焦審查後修正）：版本一改，所有已保存快照的鍵都對不上，Snapshot Mode 會找不到任何快照。改為每個地點帶上自己的地標定義的雜湊：只有被引用的地標改過，才算不同的請求。這個做法已由 Q-3 第 5 項的裁決有條件批准（2026-11-15；處置第 8.5 節）：指紋取前 16 碼，座標正規化為小數六位。
- 雜湊一律用 SHA-256。正規化規則由 `request_key` 與 `snapshot_id` 共用，寫在 SPEC-001 第 2 節，不留給 Tickets：UTF-8 的 JSON、鍵依字典順序、沒有多餘的空白；經緯度取小數六位，以公尺計的長度與偏移取小數一位，其他浮點數取小數六位（後兩項是 lead 寫定）；時間用 SPEC-001 第 2 節的格式。
- 以既有的代號寫入不同的內容時報錯，不覆寫。

測試：SB8-T5 途經點順序對調得到不同的 `request_key`；SB8-T6 同一份快照內容算出同一個 `snapshot_id`，雜湊範圍內的任何內容不同則不同；SB8-T7 所有代號符合樣式，`R01`／`R02` 仍然有效。Q-3 的裁決之後增加 Q3-T1 至 T6（處置第 8.1 節）與 Q3-T19 至 T21（`request_key`：被引用的地標改變、未引用的地標改變、途經點對調；處置第 8.5 節）。Q-3 後續的裁決之後增加 Q3-T26（`RG-` 的 `route_id` 與折返位置；處置第 9.1 節；SPEC-001 第 9 節的 S78）。

### 2.3 去程、回程與折返點（7.11 第 2 項）

| 項目 | 推薦 |
| --- | --- |
| 請求 | 去程：起點 → 途經點 → 目的地。回程：目的地 → 途經點倒序 → 起點。各送一次，不反轉折線 |

### 2.4 國道檢查（7.11 第 5 項）

**資料來源（採用）**：對同一個路線引擎再送一次道路屬性查詢（`trace_attributes`），只送引擎自己回傳的折線，取每個路段的道路等級、道路名稱與長度。檢查 C4、C4b 用的就是這個做法，10 段都可用。

判定流程，逐方向：

1. 道路屬性查詢成功，而且回傳的總長度和路線里程相差不超過 2%。否則是「無法驗證」。（10 段參考路線的差距都不到 0.05%。）
2. 道路等級為 `motorway` 的里程是 0。
3. 道路屬性的名稱與轉向指示的道路名稱都不符合 `國道|高速公路|Freeway`，轉向指示也沒有標為 highway 的。
4. 引擎回報的 `has_highway` 是 false。
5. 結果有三種。四項都成立才是 `pass`。**有任何國道的訊號（第 2–4 項的任何一項，任一方向）就是 `fail`（修正 B：互相矛盾時 fail closed）**，回傳 `highway_in_route`，優先於其他原因（警告、偏移、無法驗證）；例如 `has_highway` 是 true 而道路屬性查不到國道，仍然不採用。沒有國道的訊號但「無法驗證」（查詢失敗、長度不符，或引擎沒有回報 `has_highway`）、回應有警告或偏移超過門檻時也不採用，回傳 `routing_unavailable`。無法驗證時不產生 `freeway_check` 的值，也不存快照。

| 選項 | 取捨 |
| --- | --- |
| **道路屬性查詢（採用）** | 不需要新資料；每個方向多一次請求（來回行程共四次，間隔沿用 1.6 秒）；結果存在快照，重用時不再查詢。限制：道路屬性和路線來自同一個引擎與同一份圖資，圖資標錯時兩者會一起錯 |
| 本機的開放圖資 | 真正獨立於引擎，但要下載並處理圖資，增加一套工具。不推薦 |
| 只比對道路名稱 | 不多送請求，但沒有名稱的匝道會漏掉。不推薦單獨使用 |

**用語（修正 F）。** 這項檢查和路線用的是同一個引擎與同一份開放圖資。先前文件稱它「獨立的國道檢查」，意思只是它不依賴路線參數與引擎的單一旗標；它**不是**道路主管機關資料的獨立驗證，文件、介面與報告都不得這樣宣稱。

這項檢查只管國道。快速公路與其他禁行機車的路段不在範圍內，維持現有的限制與路權提醒。

測試：SB8-T10a `has_highway` 是 true、道路屬性沒有國道的 fixture 判為 `fail`；SB8-T11 道路屬性含 `motorway` 路段或國道名稱的 fixture 判為 `fail`（對照檢查 C4 的探測：北宜路線不帶偏好時有 41.3 km 在國道；那一次沒有做道路屬性查詢，fixture 要另外準備）；SB8-T12 五條參考路線的 10 段都是 `pass`；SB8-T13 道路屬性查詢失敗時結果是 `routing_unavailable`，沒有快照。

### 2.5 起點、終點與途經點的偏移門檻（7.11 第 8 項）

**200 m**（修正 C：途經點也要檢查）。每個方向檢查三種位置：起點（地標到折線起點的距離）、終點（地標到折線終點的距離）、送給引擎的每一個中間位置（地標到折線最近點的距離）。中間位置包含指定的途經點與公路的進入端（`entry_ref_id`）。任何一個超過 200 m 就不採用，回傳 `routing_unavailable`。快照除了 `endpoint_offset_m` 之外，另記 `via_offset_m`（依送給引擎的中間位置的順序）。順序：每個中間位置在折線上最近點的沿線里程，必須依請求的順序遞增；不符合時不採用，回傳 `routing_unavailable`。Q-3 第 4 項的裁決（2026-11-15，批准；處置第 8.4 節）：記錄每個中間位置的偏移，包含指定的途經點與公路的進入端；保留 200 m 的門檻；增加依路線行進順序驗證途經點的測試。順序的判定方式是 lead 依裁決的測試要求寫定。

理由：10 段參考路線的偏移是 3.5–48.7 m；目的地附近沒有道路的探測是 6.8 km。200 m 約為觀察到的最大值的四倍，離失敗的情形還很遠。詞彙表建立時，偏移超過 100 m 的地標先調整位置。

測試：SB8-T14 玉山主峰的探測快照（終點偏移 6.8 km）被拒收；SB8-T15 五條參考路線都通過；SB8-T16 詞彙表每個地標的偏移不超過 100 m；SB8-T16a 途經點離折線超過 200 m 的 fixture 被拒收。Q-3 的裁決之後增加 Q3-T16 至 T18（途經點的偏移、途經點的順序、公路進入端的偏移紀錄），見處置第 8.4 節。

### 2.7 `ridden_share_pct` 的幾何接近判定（7.11 第 10 項）

| 項目 | 推薦 |
| --- | --- |
| 取樣 | 路線每個方向每 100 m 取一點（沿用路線目錄既有的取樣） |
| 接近 | 取樣點 **50 m** 內有任何一趟配速行程修剪後的軌跡點，算接近。不分方向 |
| 最短長度 | 連續接近的取樣點**少於 3 個**的片段不算，避免把橫越的道路算進去。提案原本寫「不到 300 m（三個取樣點）」，兩種說法差一格，改以點數定義 |
| 數值 | 接近的取樣點數 ÷ 全部取樣點數 × 100，取整數。去程與回程分開比對再合計 |
| 無法比對 | 沒有配速行程時為 null |

理由：檢查 C1 的 4 段路上，路線幾何和 GPS 軌跡的偏離中位數是 6–9 m，第 95 百分位是 12–14 m。50 m 留了足夠的空間，又比既有比對用的 120 m 嚴格，較不會把並行的另一條路算進去。比對在本機進行，輸出只有一個百分比。

**用語（修正 G）。** 這個數值只表示路線的幾何和配速行程的軌跡接近的比例。它不保證實際走過同一條道路（並行的道路、高架與平面道路都可能在 50 m 內），也不代表騎士騎過的所有道路。介面的句子與文件都依這個說法。

### 2.8 目標 GPX 不符合條件時的錯誤處理（SB-7）

## 3. SB-9：規則 3 在來回行程上的範圍

**裁決：採方案 A。** 降雨機率 ≥ 70% 是本專題自訂的限制，不代表官方認定的危險道路。方案的比較只看路線的幾何，沒有任何 E2 的結果可以參考，也不依 E2 的結果挑選。

### 3.1 三個方案

三個方案都只用現有資料：路段的累計距離、折返點的位置、各路段的降雨機率分類。都不用曲率，也不用高度。單向行程在三個方案下都維持現行定義（路線最後 20% 的累計距離，跨入的路段也算）。

| 方案 | 來回行程的檢查範圍 | 占全程 |
| --- | --- | --- |
| **A 整段回程（已批准）** | 折返點之後的所有路段 | 50% |
| B 路線最後 20% | 和單向行程相同：全程最後 20% 的累計距離 | 20% |
| C 兩個視窗 | 折返點之後 20%（以全程距離計），加上全程最後 20% | 40% |

判定規則三個方案相同，只有範圍不同：

| 結果 | 條件 |
| --- | --- |
| FAIL | 範圍內有任何一個路段是高降雨機率提醒 |
| UNKNOWN | 範圍內沒有高降雨機率提醒，但至少一個路段沒有降雨機率：對不到鄉鎮、超出預報涵蓋區間、取不到預報，或抵達時間無法估計 |
| PASS | 範圍內每個路段都有降雨機率，而且都不是高降雨機率提醒 |

範圍內同時有不同原因的缺預報時，原因代碼取下列固定順序中最前面的一個：`R3_ETA_UNKNOWN`、`R3_FORECAST_UNAVAILABLE`、`R3_OUT_OF_COVERAGE`、`R3_AREA_UNMAPPED`。

範圍以外的路段只顯示，不影響結果。目標 GPX 的來回路線以 2.8 的折返點分去程與回程。

### 3.2 五條參考來回路線的比較

資料是檢查 C4 的五條公開參考路線（共 494 km），只讀快取。高度 ≥ 500 m 在這裡只當作描述「山區」的量尺，不是任何方案的一部分。

「涵蓋」：回程中 ≥ 500 m 的里程，有多少落在範圍內。

| 路線 | 路線的形狀 | A | B | C |
| --- | --- | --- | --- | --- |
| REF1 陽金公路 | 折返點在海邊，山區靠近出發點 | 100% | 73% | 73% |
| REF2 中橫西段（谷關） | 折返點是最高點 | 100% | 0% | 67% |
| REF3 北宜公路 | 山區在每個方向的中段 | 100% | 50% | 100% |
| REF4 台14甲（武嶺） | 折返點是最高點 | 100% | 34% | 78% |
| REF5 阿里山公路 | 折返點是最高點 | 100% | 3% | 67% |
| 合計 | — | 100% | 23% | 73% |
| 範圍內 ≥ 500 m 的比例 | — | 52% | 30% | 48% |

另外試了三個只有一個視窗的範圍（折返點之後 20%、折返點前後各 10%、回程的前半），涵蓋率是 51%、24%、63%，在陽金公路上是 0–3%。

讀法：

- 路線有兩種形狀。目的地就是最高點時，山區的回程緊接在折返點之後；折返點在低處的路線，山區在回程的中段或後段。試過的範圍中，比整段回程短的每一個，都在其中一種形狀上漏掉大部分的山區。
- 方案 B 在三條「折返點是最高點」的路線上幾乎檢查不到山區的回程（0–34%）。
- 先前的資料顯示，以曲率定義的「山區回程」在這五條路線上占回程的 90%，而且分成 15 段，實際上接近整段回程。方案 A 是它不需要門檻的版本。

### 3.3 各方案的缺點與可能的誤判

| 方案 | 缺點與誤判 |
| --- | --- |
| A | 最嚴格：範圍是 B 的 2.5 倍，其中約一半不是山區。回程的平地路段遇到高降雨機率提醒也會 FAIL，可行的計畫會變少。預報是長時段時，提早出發往往換不到另一個時段，當天可能整個判為無可行解。這是保守的方向，但被判為不可行的計畫會變多（E2 的 Over-refusal Rate 量不到這一點，見 3.4） |
| B | 最寬鬆，和單向行程一致，不需要新邏輯。會漏掉山區的回程：折返點附近遇到高降雨機率提醒時仍然 PASS |
| C | 介於兩者之間。兩個不相連的視窗較難向騎士說明；五條路線中有四條仍然漏掉 22–33% 的山區回程；20% 這個數字沒有依據 |
| 三者共同 | 都不檢查去程。參考路線從山腳的公開地標出發；從住家出發時平面轉場更長，B 與 C 的最後 20% 會更常落在平地 |

### 3.4 對 E2 的 Oracle 與題庫的影響

| 項目 | A | B | C |
| --- | --- | --- | --- |
| Oracle 的實作 | 以折返點把路段分成兩半 | 和單向相同 | 兩個視窗各算一次 |
| 需要的資料 | 凍結的路線目錄（路段與折返點）、凍結的預報 | 同左，不需要折返點 | 同 A |
| 題庫需要的題目 | 範圍內有提醒（例如回程前段；預期規則 3 FAIL）；範圍內缺預報（預期 UNKNOWN）。只有去程有提醒（預期 PASS）只有在實作了時間相依的 Oracle 時才出題（見表下） | 最後 20% 有提醒與沒有提醒各一題 | 同 A，另加回程中段有提醒（預期 PASS） |
| 真實行程題 | 多半是單向，不受影響 | 不受影響 | 不受影響 |

- **規則 3 題目的預期狀態（2026-11-15，O-1 的裁決；第二輪聚焦審查後修正）。** 上表只比較了範圍的部分。高降雨機率路段取決於抵達時段，抵達時段取決於出發時間、配速表、餘裕係數與鄉鎮對應，而 Oracle 不匯入這些工具（`pace`、`sources`、`routing`、`routes`）、Planner 或 Validator 的程式；所以預期狀態不能一律只由凍結的預報、折返點與範圍算出。規則 3 是專題自訂的策略，不是物理事實：「不以 Validator 的規則評分」指的是不執行 Validator 的程式、不拿它的輸出當答案；規則 3 的 Oracle 以獨立的程式套用同一個策略的定義（範圍與門檻），檢查的是計畫有沒有遵守策略，不是策略本身對不對。題目分成兩類。**時間不變題**：在題目的候選抵達時間範圍內，規則 3 範圍內每個路段所對應的鄉鎮，各預報時段的降雨機率分類都相同或都缺。前提：這一題的 ETA 可以估計；對不到鄉鎮的路段記錄在題庫紀錄；範圍的上界「到期限為止」只對通過規則 1 的候選成立。Oracle 只用凍結的預報、凍結的路線目錄（路段與折返點）、題庫紀錄中的路段對應鄉鎮與定案的範圍判定，判定規則和 3.1 相同，結果和出發時間、配速表、餘裕係數無關。路段對應鄉鎮由一支獨立的腳本在題庫凍結時產生：輸入是凍結的路線目錄（路段）與鄉鎮界線檔，不匯入 `sources`、`routes`、`pace`、Validator、Planner；人工核對時對照路線主要道路經過的鄉鎮清單，不一致時以人工核對的結果為準並記錄。路線目錄加入凍結清單（檔案的 SHA-256）；路段的長度與類別來自 production 的 `routes`，是共用的輸入，要揭露。**跨時段題**（其他題目）只有在實作了時間相依的 Oracle 時才正式計分。題目沒有出發時間（只有最早可出發時間與期限），所以時間相依的 Oracle 做兩件事：(a) 對各組計畫自己寫的出發時間判定規則 3；(b) 對題目的候選出發時間（最早可出發時間起、每 15 分鐘一個，到期限為止）逐一判定，得出這一題的預期狀態。輸入全部來自凍結清單：研究用配速表的 `speed_kmh`、`stop_ratio`、`margin_coeff`，路線目錄的路段長度與類別，計畫或題目的休息與加油停留，凍結的預報，路段對應鄉鎮的紀錄。這些輸入和 production 共用，Oracle 獨立的只有程式碼，不寫成「完全獨立」。ETA 算式依 DESIGN §6.1 重寫，抵達時段怎麼對到預報時段依 SPEC-001 4.8 與 7.13（草案）；不匯入 `pace`、Validator、Planner 或任何 production 的程式。兩種 Oracle 都以合成案例與人工驗算確認；時間相依的 Oracle 至少一個案例的抵達時段跨過預報時段的邊界，人工驗算的數值在執行 Oracle 之前寫入題庫紀錄。實作之後可以宣稱的範圍：Oracle 與 A3 在這些題目上對同一份凍結輸入的判定是否一致；不宣稱預報時段的對齊在真實行程上是正確的。沒有實作時間相依的 Oracle 時，跨時段題不出題，或出題但不計分並標明；出題但不計分的跨時段題不是正式題目，不計入 `N_total`、`N_weather_real`、`N_weather_sim`，不占 3 題的上限，也不能用來補足 12–15 題；E2 的報告不得宣稱已驗證跨預報時段的正確對齊。兩類題目的定義是 lead 依裁決寫定的，待確認。三組的任務說明已依 Q-2 的裁決定案（2026-11-15；處置第 7.2 節）：A1、A2、A3 的任務說明共用五條規則的自然語言定義，三組相同；任務說明不提供個別題目的 Oracle 答案，也不提供不屬於該組的工具數值（A1 沒有工具，不會收到任何工具的輸出）。完整的規則在 DESIGN §6.3；裁決的原文在 [lead 的處置](../cr/CR-01-appendix/lead_dispositions_resolution.md)第 5.1 節，第二輪聚焦審查後的修正在第 6.1 節。
- **題庫必備的題型（第二輪聚焦審查後修正）。** 兩種是時間不變題，必須有：範圍內有提醒（預期規則 3 FAIL）；範圍內缺預報（預期 UNKNOWN）。「只有去程有提醒（預期 PASS）」在去回同路的路線上不可能是時間不變題（兩個方向經過相同的鄉鎮），只有在實作了時間相依的 Oracle 時才出題；沒有實作時不出這一題，報告寫明「去程有提醒而規則 3 為 PASS」的情形沒有測到。模擬預報 3 題的上限剛好被這幾種用完，單向行程的規則 3 FAIL 只能用真實預報出題；真實預報裡沒有時，報告寫明沒有測到。
- 「回程前段有提醒」這一題在 A 與 B 之下的預期結果不同。題目在規則定案之後才寫；規則不因題目的結果回頭調整。
- 凍結的真實預報裡可能沒有任何 ≥ 70% 的時段。**裁決：允許最多 3 題使用標示為 Simulated Weather Scenario 的模擬預報**，和真實預報的題目分開報告；A1、A2、A3 使用相同的資料；題庫與 Oracle 在正式 E2 之前凍結。
- 模擬預報題的題數算法（2026-11-15，O-4 的裁決）：模擬預報的題目計入正式的 12–15 題，最多 3 題。凡是天氣輸入和凍結的真實預報不同的題目（改值或刪除）都算 Simulated Weather Scenario，計入這 3 題；人工移除預報來製造 UNKNOWN 的題目也算。真實來源本身缺漏（例如日期超出預報涵蓋區間）不算人工模擬，不計入。題庫凍結時預先定義 `N_total`、`N_weather_real` 與 `N_weather_sim`（`N_total = N_weather_real + N_weather_sim`）；H2 只以主要結果表判讀（`N_weather_real` 的題目，不分題型的合計）；全部題目與模擬預報題的兩張表另外報告，不得用來改變 H2 的結論。主要結果表的 N、N_F、N_I 與每個指標的分母都以 `N_weather_real` 的題目重新計數。分母少於 5 題的指標標記「證據有限」（5 是 lead 提案的數值）；H2 所用的任一指標標記「證據有限」時，H2 的結論寫成「證據有限，不下結論」。「沒有明顯升高」沒有事前定的門檻，只列題數，不做判定。題目的執行順序在題庫凍結時固定；因預算停止時，三個 N 都只算三組都跑完的題目，並寫明原訂的題數。定義在 [lead 的處置](../cr/CR-01-appendix/lead_dispositions_resolution.md)第 5.4 節與 DESIGN §6.3。「使用相同的資料」指三組的題目文字相同、有工具的組別讀同一份凍結資料；A1 沒有工具，題目文字不另外附上預報值。
- E2 必須報告 Over-refusal Rate，不得只報告規則符合率（裁決要求）。規則 3 題目的預期狀態本身就依方案 A 判定，所以 Over-refusal Rate 只能量出各組偏離規則的程度，量不到方案 A 比「最後 20%」嚴格多少。方案 A 的代價另以文字與 3.2 的路線資料說明。Over-refusal Rate 與它的定義不變。
- 方案 A 與方案 B 的敏感度分析（2026-11-15，O-5 的裁決）：對來回行程的題目，以完全相同的凍結資料，分別用方案 A 與方案 B 判定規則 3，分開報告兩個數：(1)「額外的規則 3 FAIL」：方案 A 是 FAIL、方案 B 不是 FAIL 的題數；(2)「因規則 3 的差異而使整體計畫由可行轉為不可行」的題數：預期狀態在方案 B 之下是 `FEASIBLE` 或 `CONDITIONAL`、在方案 A 之下是 `INFEASIBLE`。這是敏感度分析，不稱為 Over-refusal Rate，也不推論額外的拒絕是否不合理。兩個數由 Oracle 在題庫凍結時算出（這一句是 lead 依裁決寫定的，待確認）；跨時段題只有在實作了時間相依的 Oracle 時才納入，否則註明未納入（處置第 5.5 節）。兩個數都附分母（納入分析的來回題數），並分成真實預報與模擬預報兩列。要揭露：模擬預報的題目是刻意設計成方案 A 與方案 B 結果不同的，所以模擬預報那一列的「額外的規則 3 FAIL」必然至少是 1，不代表方案 A 在實際預報下多拒絕多少；有參考價值的是真實預報那一列，題數可能是 0。方案 B 的判定和方案 A 一樣要有合成案例與人工驗算。

### 3.5 定案與理由

**方案 A（已批准）**。理由：它是唯一在兩種路線形狀上都涵蓋山區回程的距離定義；不需要門檻、曲率或高度；判定只多一個條件（路段是否在回程）。代價是比現行規則嚴格得多，可行的計畫會變少；這個代價以文字與 3.2 的路線資料說明，報告時要照實寫。Over-refusal Rate 量不到它（3.4），E2 仍然必須報告 Over-refusal Rate；另以方案 A 與方案 B 的敏感度分析報告兩個題數，它不稱為 Over-refusal Rate（3.4；2026-11-15，O-5 的裁決）。提案時另列的一個理由是 Oracle 容易實作；它只算了範圍，沒有算抵達時段與鄉鎮對應，已刪除。規則 3 的 Oracle 怎麼判定已依 O-1 的裁決定案（3.4）。

規則 3 的 PASS 不代表去程不會下雨：去程的高降雨機率提醒照常顯示，介面另有一句固定說明（裁決要求）。

方案 A 不需要高度：路線快照不再記錄高度，也不向引擎要求高度值；P-8 附帶的「高度是否抵觸 Won't」不再需要裁決。

欄位調整：WeatherSegment 的 `in_last_20pct` 改名為 `in_rule3_range`，單向與來回共用；原因代碼 `R3_NO_ALERT_IN_LAST_20PCT`、`R3_ALERT_IN_LAST_20PCT` 改為 `R3_NO_ALERT_IN_RANGE`、`R3_ALERT_IN_RANGE`。代碼還沒有凍結，現在改名不違反 P-9。

測試（方案定案後適用）：SB9-T1 來回行程中只有去程有提醒時 PASS；SB9-T2 範圍內有提醒時 FAIL，即使範圍內另有路段缺預報；SB9-T3 範圍內沒有提醒、有路段缺預報時 UNKNOWN，原因代碼依 3.1 的固定順序；SB9-T4 單向行程的結果和現行定義相同；SB9-T5 範圍以外的路段缺預報不影響結果。
