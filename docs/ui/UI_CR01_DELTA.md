## 1. 目的

CR-01 恢復了 Proposal 的核心體驗：歷史 GPX 的個人化配速、自然語言的行程描述、實際道路的路線、當天來回。這些改變集中在輸入的方式與路線的來源。三個畫面的結構、狀態標籤、UNKNOWN 的呈現與來源證據都不變。

這份文件做三件事：

1. 說明哪些內容維持凍結（第 2 節）。
2. 說明新增與修改的內容（第 3–8 節）、專題負責人接受的簡化（第 9 節）與來回行程的天氣呈現（第 10 節）。
3. 對照到驗收條件與 Streamlit 1.67.0 的標準元件（第 11、12 節）。

沒有新一輪的需求討論，也沒有重新設計介面。

## 3. Profile 區（Must）

CR-01 的裁決 D1：歷史 GPX 的多檔介面上傳、合併去重複、Profile 更新與涵蓋度摘要是 Must，不能只做指令匯入；不得硬性要求至少五份 GPX。

這裡的 Profile 指由歷史 GPX 建立的個人配速表。Rider Profile 設定檔（油箱容量、平均油耗、休息習慣等）仍是靜態檔案，介面不提供編輯。

### 3.1 位置

頁首之下、Trip Planner 之上，一個可展開的區塊，標題是「騎士 Profile 與歷史 GPX」。還沒有配速表時預設展開，已經有配速表時預設收合。它不是第四個畫面，也不在分頁裡。

### 3.2 內容

| 內容 | 說明 | Streamlit 1.67.0 |
| --- | --- | --- |
| 涵蓋度摘要：三個數值 | 可用的行程數、可用的路段數、累計公里 | `st.metric` 三張 |
| 涵蓋度摘要：各類別的資料量 | 每個類別一列：類別、路段數、來自幾趟、資料夠不夠 | `st.table` |
| 白話說明 | 依資料量顯示其中一則，見 3.3 | `st.info` 或 `st.warning` |
| 選取歷史 GPX | 一次可以選多個檔案，只接受 `.gpx` | `st.file_uploader`（`accept_multiple_files=True`） |
| 「更新 Profile」按鈕 | 按下後才處理：合併到行程清單、以檔案內容去重複、重建配速表、更新摘要。合併的規則見表後 | `st.button` |
| 處理進度 | 步驟文字，不顯示百分比。顯示在 Profile 區的可展開區塊之外，緊接在它下方 | `st.status` |
| 處理結果 | 新增幾個檔案、略過幾個內容重複的檔案、幾個檔案無法讀取與原因 | `st.info`；有檔案無法讀取時用 `st.warning` |
| 隱私說明 | 固定文字，見 3.4 | `st.caption` |

類別沿用配速表的三類，介面寫成白話：低曲率（直路與緩彎）、中曲率（一般彎道）、高曲率（連續彎道）。

**合併的規則。** 行程清單是 `trip_id` 的唯一來源。新上傳的檔案以內容去重複後接續編號；已經指定的 `trip_id` 不變動，重複上傳、改檔名或改變上傳順序都不會讓既有的行程換編號。研究用的保留行程是以 `trip_id` 的清單凍結的，所以這一條不能違反（SPEC-001 第 2 節）。

### 3.3 資料少時的說法

沒有最少檔數的限制：一個檔案也可以更新 Profile。資料夠不夠只看每個類別的路段數有沒有達到配速表的最低要求（目前的暫行值是 30 段，定義在配速表的建立規則），不另外分級。摘要中的「來自幾趟」只用來顯示，不是資料夠不夠的條件。

| 情形 | 顯示的文字（提案） |
| --- | --- |
| 還沒有任何歷史 GPX | 還沒有歷史 GPX。沒有個人配速表時，系統無法估計抵達時間，和時間有關的規則會顯示 UNKNOWN。上傳一個檔案就可以開始。 |
| 某個類別的路段不夠 | 〈類別〉的路段還不夠（目前 N 段，需要 30 段）。路線含有這類路段時，系統無法估計抵達時間，會如實顯示 UNKNOWN。再上傳含有這類路段的行程就可以補上。 |
| 三個類別都夠 | 三個類別的資料都足夠估計。新的 GPX 可以隨時再加入。 |

資料不足時系統不以其他類別的數值代替（CR-01 第 6 節：缺類別時整條路線為 UNKNOWN 的規則保留）。

### 3.4 隱私

- 固定文字（2026-11-15 裁決，U-7）：「歷史 GPX 僅供本服務建立個人配速資料，不會傳送給外部語言模型或路線服務。畫面只顯示彙總資訊。」這句話不宣稱檔案只在使用者自己的電腦上處理；它承諾的是歷史 GPX 不送給外部的語言模型或路線服務，後續的實作要驗證這個承諾（SPEC-001 的 S22 與路線請求只使用公開地標的規則）。
- 摘要不顯示座標、騎乘的日期與時間，也不顯示私有的路線名稱；不逐趟列出行程。
- 上傳元件本身會顯示剛選取的檔名，這是元件的行為。處理結果只在檔案無法讀取時列出檔名。
- 研究用的保留行程不進配速表（CR-01 第 13 節），也不計入摘要。
- 語言模型的 API 也是外部服務。歷史 GPX、逐趟的騎乘資料與住家位置不送給語言模型；送出去的只有通過本機輸入保護的行程文字（第 4 節）、結構化的條件，以及不含座標與軌跡點的工具輸出（SPEC-001 第 2 節）。

### 3.5 和規劃結果的關係

Profile 更新後配速表的版本改變。畫面上如果有舊的規劃結果，要標示為過期，直到再按一次「規劃」。更新 Profile 本身不會觸發規劃。

| 還沒選 | 欄位標示為「期限」，下方說明「來回：最晚回到出發點的時間；單向：最晚抵達終點的時間」。規劃後，採用的條件使用上面兩個名稱之一 |

起點是出發錨點（代替住家的公開地標）時，期限欄位下方固定說明：「出發點不是住家；回到家的時間請自行加上。」起點是詞彙表中的其他公開地標時不顯示這一句。

目標路線 GPX 不會被系統推定為來回行程（審查處置的修正 3）。行程型態只來自表單、行程描述或追問。騎士指定來回時，GPX 的終點要回到起點（相距 200 公尺以內）才當成來回行程；只指定折返點不足以證明有回程（SPEC-RESOLUTION-001 修正 E，2026-11-15 裁決）。折返點依 Q-3 第 2 項的裁決（2026-11-15；SPEC-001 第 7.11 節第 2 項）：軌跡明確去回同路時，系統自動取離起點最遠的軌跡點；環狀、8 字形等有歧義的軌跡不自動推定，要由騎士指定折返位置（距起點的公里數）。折返位置先由 CLI 指定；介面上選填的「折返位置」欄位是 Should，不是第一張 Streamlit Ticket（UI-0）的 Must。介面沒有這個欄位時，有歧義的目標路線 GPX 在介面上只會顯示下面第二種路線錯誤。騎士指定的合法折返位置優先於自動判定。自動辨識的門檻是保守的啟發式，沒有以真實資料驗證過，介面與說明不得宣稱它經過驗證（2026-11-15 的裁決；SPEC-001 第 5.4 節）。下列兩種情形不規劃，顯示路線錯誤（第 7.1 節）。終點沒有回到起點時（即使填了折返位置）：「這個 GPX 不是來回的路線：終點沒有回到起點。請改選單向，或提供含回程的 GPX。」終點回到起點但無法確認折返點時（軌跡有歧義而沒有指定折返位置，或指定的里程不合法）：訊息說明無法確認折返點，請指定折返位置或改選單向（文字是提案，與 SPEC-001 第 5.5 節相同）。系統不推定、不反轉，也不補造回程。騎士指定單向時，GPX 的幾何原樣使用，不使用折返位置。

**欄位檢查的變化。** 行程描述與目標路線 GPX 都沒有提供時不進入規劃，錯誤摘要與欄位旁的錯誤照 G3 的做法顯示。其他檢查不變。

**衝突的處理不變。** 行程描述和表單不一致時以表單為準，並在結果中提示。CR-01 之後會發生衝突的欄位是行程型態、日期、時間、油量；另外，行程描述寫了路線、同時又提供目標路線 GPX 時，以 GPX 為準並提示。

**目標路線 GPX 的介面上傳是 Should**，不在這次的 Must。做的時候用單檔的 `st.file_uploader`，取代檔案路徑的文字欄。選填的「折返位置」欄位同樣是 Should（2026-11-15 的裁決）。

## 5. 追問

追問仍然只在缺少必要條件或有歧義時出現，位置不變（規劃進度的下方）。

| 項目 | G3 | CR-01 之後 |
| --- | --- | --- |
| 追問的主題 | 休息安排有歧義 | 缺起點；不知道從公路的哪一端進；沒說來回或單向；休息多久 |
| 一次問幾題 | 一題 | 把缺少的項目一次列在同一個區塊，每一題一組選項 |
| 選項的來源 | 固定選項 | 起點與進入端的選項只來自詞彙表與 Rider Profile；行程型態是來回或單向；休息長度是固定選項 |
| 騎士要求的休息對應不到地點（2026-11-15，Q-1 的裁決） | 沒有這個情形 | 放進同一次追問，每一段休息一題。文字由程式依固定模板產生，列出行程描述中的原文；選項固定：這次指定的各個途經點的名稱、「折返點」（只有已知是來回行程時）、「不安排這段休息」。選「不安排這段休息」只取消那一段休息，不代表整趟不休息（第 8 節的休息策略）。規則與文字見 SPEC-001 第 4.1、4.2、5.5 節 |
| 來回行程、途經點的休息沒有寫方向（2026-11-15，Q-3 第 3 項的裁決） | 沒有這個情形 | 去程與回程都會經過那個途經點，系統不自行決定方向。放進同一次追問，每一段休息一題。文字由程式依固定模板產生，列出行程描述中的原文；選項固定：「去程」「回程」「不安排這段休息」（文字是提案）。行程描述已寫明去程或回程時不問。這一題只用在來回行程、而且那個途經點在去程與回程各經過一次的情形；單向行程不需要選。規則與文字見 SPEC-001 第 4.1、4.2、5.5 節 |
| 行程型態與休息方向在同一輪（2026-11-15 的裁決） | 沒有這個情形 | 行程型態還不知道、又有途經點的休息沒有寫方向時，行程型態的那一題和方向的那一題放在同一次追問，不增加第二輪。方向的那一題標明「選擇來回時才需要回答」（文字是提案）；回覆來回時依所選的方向安排，回覆單向時這一題的回答不使用。規則與文字見 SPEC-001 第 4.1、4.2、5.5 節 |
| 回覆 | 選取後按回覆 | 全部選完後按一次「回覆並繼續規劃」 |
| 輪數 | 一輪 | 一輪。回覆後仍無法決定路線時顯示路線錯誤（第 7 節），不再追問。回覆後休息仍然對應不到地點時回到表單，顯示固定訊息（第 7.1 節），也不再追問 |

這不是聊天：沒有對話輸入框，沒有多輪往返，結果產生後也沒有自由對話（UI_ACCEPTANCE A2 不變）。

Streamlit 的做法：一個 `st.chat_message` 區塊說明缺少什麼，裡面每一題一個 `st.radio` 或 `st.selectbox`，最後一個 `st.button`。不使用 `st.chat_input`。

## 6. 路線確認區塊

路線取得之後顯示，位置在追問之下、結果過期的提示之上。兩個分頁都看得到它。它讓騎士確認系統採用的是哪一條路；它不是按鈕，不擋住規劃，也不增加強制的點擊（審查處置 P-11）。騎士不同意這條路線時，修改行程描述後再按一次「規劃」。

| 內容 | 說明 | Streamlit 1.67.0 |
| --- | --- | --- |
| 行程型態與起訖 | 來回或單向；起點、目的地或公路、途經點的名稱 | 文字 |
| 里程 | 整條路線的公里數；來回行程包含回程 | `st.metric` |
| 主要道路名稱 | 依行經順序列出。只有名稱，沒有座標，沒有地圖 | 文字清單 |
| 路線來源的標籤 | 「路線引擎」「目標路線 GPX」「示範路線」三者之一，灰色 | `st.badge` |
| 路線快照的標籤 | 路線來自路線快照時顯示「資料快照」（藍色），附快照的時間 | `st.badge` 加文字 |
| 去回里程差的提示 | 只在來回行程的去程與回程里程相差超過 2% 時顯示（`route.leg_length_diff_flag`）。固定句子，見下方 | `st.info` |
| 路權提醒 | 固定句子，見下方 | `st.caption` 或 `st.info` |

整個區塊放在 `st.container(border=True)` 裡。

**固定句子**（提案；文字與 SPEC-001 第 5.5 節相同，不由語言模型產生）：

- 路線來自路線引擎時：「這條路線由路線引擎依開放圖資產生。系統用同一份開放圖資再檢查一次，沒有發現國道路段；這不是道路主管機關的驗證。其他道路的機車通行限制（例如部分快速公路與高架道路）系統無法保證，請出發前自行確認路權。」
- 路線來自目標路線 GPX 或示範路線時：「這條路線取自你提供的 GPX 或騎過的行程。系統沒有檢查國道與機車通行限制，請出發前自行確認路權。」
- 去回里程差超過 2% 時（2026-11-15 依裁決修正，U-14）：「去程與回程分別計算，里程相差約 N%。實際經過的道路可能不同，請核對道路名稱。」

「再檢查一次，沒有發現國道路段」指的是系統的國道檢查：每個方向的所有訊號都沒有國道，才採用這條路線（SPEC-001 第 7.11 節第 5 項）。這項檢查和路線用的是同一個引擎與同一份開放圖資，所以句子寫明它不是道路主管機關的驗證；介面與說明都不把它稱為獨立的驗證（SPEC-RESOLUTION-001 修正 F，2026-11-15 裁決）。句子不寫「已排除」：路線參數是 `use_highways: 0`（審查處置 P-1），它是偏好，不是保證。這個設定可能連快速公路也避開，路線會比較慢。

路線引擎回報的行駛時間不顯示，避免和個人的典型估計、保守估計混淆。

## 7. 路線錯誤與評估失敗

CR-01 的裁決 D2：路線服務失敗時不得讓語言模型編造路線，必須有驗證過的快照或明確的錯誤處理。

### 7.1 路線錯誤

出現的六種情形與畫面上的文字（提案；與 SPEC-001 第 5.5 節相同）。第六種依 SPEC-RESOLUTION-001（2026-11-15 裁決）新增；它有兩則文字，第二則依 Q-3 第 2 項的裁決新增（2026-11-15）：

| 情形 | 錯誤訊息 | 騎士可以怎麼做 |
| --- | --- | --- |
| 行程描述中的公路或地標不在詞彙表內 | 行程描述中的「〈名稱〉」不在目前支援的公路與地標清單內，系統沒有產生路線。 | 改用清單內的公路或地標重新描述；或提供目標路線 GPX。 |
| 路線服務沒有回應、回傳錯誤，或找不到可用的路線；回應帶有警告；起點、終點或途經點離路線超過 200 公尺，或途經點在路線上的順序和請求不同；國道檢查無法完成 | 系統無法產生可採用的路線。（2026-11-15 依裁決修正，U-16） | 請檢查起訖點與途經點，或改用已有的路線快照／目標 GPX。如果是路線服務暫時無法使用，請稍後再試。 |
| 回傳的路線沒有通過國道檢查（任何一項訊號顯示有國道） | 路線服務回傳的路線沒有通過國道檢查，系統不採用這條路線。 | 增加途經點讓路線避開國道；或提供目標路線 GPX。 |
| Snapshot Mode 下沒有可用的路線快照：沒有對應的快照，或只有國道檢查的方法和現行不同的快照 | Snapshot Mode 只使用已保存的路線快照，這個行程沒有對應的快照。 | 關閉 Snapshot Mode 後重新規劃；或改成有快照的行程。 |
| 目標路線 GPX 無法使用：讀不到軌跡點、總長度不到 1 公里，或點距太疏 | 目標路線 GPX 無法當成路線使用：讀不到軌跡點、路線太短，或點與點之間的距離太遠。 | 確認檔案路徑與內容；改用記錄較密的 GPX；或改用行程描述。 |
| 騎士指定來回，但目標路線 GPX 不能當成來回的路線：終點沒有回到起點；或終點回到起點，但無法確認折返點（軌跡不是明確的去回同路，而且沒有指定折返位置，或指定的里程不合法）。介面沒有折返位置欄位時（它是 Should），有歧義的 GPX 在介面上只會得到這一則訊息 | 終點沒有回到起點時：這個 GPX 不是來回的路線：終點沒有回到起點。無法確認折返點時：系統無法確認這個 GPX 的折返點：軌跡不是明確的去回同路，而且沒有指定折返位置，或指定的位置不在軌跡的範圍內。 | 終點沒有回到起點時：請改選單向，或提供含回程的 GPX。無法確認折返點時：指定折返位置（距起點的公里數，大於 0、小於軌跡總長）；或改選單向。 |

騎士明確要求的休息排不進這條路線時，必須由確定性的程式回報，不靠語言模型自己發現；沒有把指定的休息算進抵達時間的計畫，不當成有效的計畫（2026-11-15，O-2 的裁決）。做法已依 Q-1 的裁決定案（2026-11-15，有條件批准；規則的定義處是 SPEC-001 第 4.1 節），這裡只寫畫面。休息對應不到地點不是路線錯誤，路線錯誤仍是六種。它放進既有的那一次追問（第 5 節）；追問之後仍然對應不到時不產生計畫，回到表單，在行程描述欄下方顯示固定訊息（文字是提案，與 SPEC-001 第 5.5 節相同），不再追問。「以追問回報、追問之後由表單的檢查擋下」是 lead 依 Q-1 的裁決寫定的做法，已由 Q-3 第 3 項的裁決接受（2026-11-15）。來回行程途經點的休息沒有寫方向時，也放進那一次追問（第 5 節）。lead 先前定的第七種路線錯誤不採用。依 Rider Profile 排入的預設休息排不進去時就不排，不顯示錯誤。

三點說明：

- 一般模式下，請求相同、30 天內取得的路線快照會直接重用，不呼叫路線服務；這時路線確認區塊有「資料快照」的標籤（SPEC-001 第 7.11 節第 3 項）。
- 沒有可重用的快照、路線服務又失敗時，系統不會改用已失效的快照（請求不同、超過 30 天，或國道檢查的方法改過）。騎士可以自己開啟 Snapshot Mode，讀已保存的快照。
- 路線參數是 `use_highways: 0`（審查處置 P-1）。回應帶有任何警告時不採用這條路線，顯示 `routing_unavailable` 的訊息（SPEC-001 第 4.13 節與第 7.11 節第 7 項）。起點、終點或任何一個途經點（含公路的進入端）的偏移超過 200 公尺、途經點在路線上的順序和請求不同，或國道檢查無法驗證時，也顯示同一則訊息。這些情形同時有任何國道的訊號時，顯示的是國道檢查沒通過的訊息。

畫面：

- 路線確認區塊的位置改顯示錯誤訊息與「可以怎麼做」的清單（`st.error` 加文字清單）。
- 不顯示計畫狀態標籤、出發時間與任何路線的里程或道路名稱。
- 兩個分頁顯示「沒有可用的路線，尚未規劃」。
- 仍顯示採用的條件（騎士輸入的內容）。

### 7.2 評估失敗

候選的評估因為程式錯誤或中止而沒有完成時：

- 顯示固定訊息（提案；與 SPEC-001 第 5.5 節相同）：候選的評估沒有完成，這次不提供建議的出發時間。請再按一次「規劃」；仍然失敗時，改用 Snapshot Mode 或稍後再試。
- 不顯示計畫狀態標籤，不顯示建議的出發時間，不出現「最晚的可行出發時間」，也不說無可行解。
- 路線確認區塊、採用的條件與來源證據照常顯示。

工具回傳 UNKNOWN 不算評估失敗；那種情形照 G3 的做法顯示 UNKNOWN 與待確認事項。

### 7.3 三種錯誤共用一個版面

路線錯誤、評估失敗與輸出驗證錯誤的版面相同：一則錯誤訊息、可以怎麼做、沒有計畫狀態標籤，仍顯示採用的條件與現有的來源證據。差別只在訊息的內容，以及路線錯誤時沒有路線確認區塊。

| 加油安排 | 原表格 | 來回行程增加一欄「去程／回程」。回程也經過同一個加油站時，它在去程與回程各有一列 | `st.table` 或 `st.dataframe` |
| 來源證據 | 原表格 | 增加一列路線：路線快照（資料快照，藍色）或本地衍生資料（灰色）。個人配速表那一列的涵蓋範圍寫可用的行程數與路段數 | `st.table` 或 `st.dataframe` |

Trip Result 的內容順序：狀態標籤、待確認事項、四張數值卡片、抵達時間的固定句子、路線摘要、配速資料涵蓋比例的句子、說明、採用的條件、加油安排、天氣、來源證據。

**配速資料涵蓋比例的句子**（提案；文字與 SPEC-001 第 5.5 節相同）：

| 情形 | 文字 |
| --- | --- |
| 有接近的里程 | 配速資料中的路線涵蓋比例：這條路線約有 N% 的里程，幾何和你的配速資料接近（不分方向）。這個比例只比對用來建立個人配速表的行程；它不保證你實際走過同一條道路，也不代表你騎過的所有道路。抵達時間依你的個人配速表估計；配速資料沒有涵蓋的路段，估計的可信度較低。 |
| 沒有接近的里程 | 配速資料中的路線涵蓋比例：0%。配速資料中沒有幾何和這條路線接近的行程；這不表示你沒有騎過這條路，這個比例也不代表你騎過的所有道路。抵達時間依你在同類彎道上的個人配速估計，可信度較低。 |
| 無法比對 | 系統無法算出配速資料中的路線涵蓋比例。 |

涵蓋比例只用來告知。它不改變任何規則結果，不分級，也不影響計畫狀態。「接近」的判定（取樣點 50 公尺內有配速行程的軌跡點；連續接近的取樣點少於 3 個的片段不算）見 SPEC-001 第 7.11 節第 10 項。

**排不進去的休息（2026-11-15，O-2 與 Q-1 的裁決）。** Trip Result 沒有「排不進去的休息」的訊息：`adopted_conditions.unplaced_breaks` 與待確認事項中對應的固定訊息維持撤回。指定的途經點是可以排休息的地點（O-2 的裁決），所以在途經點休息的要求會排入計畫，抵達時間含它。騎士明確要求的休息對應不到地點時，在產生結果之前就以追問或表單的訊息處理（第 5、7.1 節；Q-1 的裁決），所以 Trip Result 沒有對應的訊息。排入的休息列在「採用的條件」，騎士可以從那裡看到排入了哪些休息（SPEC-001 第 4.1 節）。

**CR-01 之後的畫面狀態。**

| 狀態 | 和 G3 相比 | 畫面 |
| --- | --- | --- |
| 待輸入 | 不變 | 兩個分頁都顯示「尚未規劃」 |
| 欄位錯誤 | 檢查的欄位改變（第 4 節） | 錯誤摘要與欄位旁的錯誤 |

狀態的數目仍是八個，因為 CR-01 新增了兩種錯誤的原因。減少的是狀態之內的變化：

- 「有計畫」原本有計畫狀態、搜尋狀態、說明來源、資料模式四個面向，共十六種組合；現在是計畫狀態與資料模式兩個面向，共四種。Planner 的補充說明有或沒有，只差一段文字，不是另一種版面。
- 取消的呈現：搜尋未完成的標籤、標題與提示；「已改用固定模板」的提示；候選被選取之後的區塊；「最接近時間限制的候選」的名稱。

## 10. 來回行程的天氣呈現（已裁決：方案 A）

規則 3 在來回行程上的範圍（CR-01 的 D3）已在 2026-11-15 裁決，採方案 A（[SPEC-RESOLUTION-001](../spec/SPEC-RESOLUTION-001-sb2-sb8-sb9.md) 第 3 節與第 8 節）：來回行程檢查折返點之後的全部回程；單向行程維持路線最後 20% 的累計距離。降雨機率 ≥ 70% 是本專題自訂的限制，不代表官方認定的危險道路。

- 單向行程的天氣表不變：前段、中段與最後 20% 三列，最後 20% 是規則 3 的範圍。
- 來回行程的天氣表分成去程與回程。回程標示為規則 3 的範圍；去程只顯示，不影響規則 3 的結果（欄位是 `in_rule3_range`，SPEC-001 第 4.8 節）。
- 去程的高降雨機率提醒照常顯示。去程有高降雨機率提醒時，表格下方固定顯示（提案；文字與 SPEC-001 第 5.5 節相同）：「去程有路段是高降雨機率提醒。規則 3 在來回行程只檢查回程，所以規則 3 的 PASS 不代表去程不會下雨。」
- 目標路線 GPX 的來回路線，以折返點分去程與回程：騎士指定了合法的折返位置時用它；沒有指定而軌跡明確去回同路時是離起點最遠的軌跡點（第 4 節）。
- 去程與回程各分成幾列、欄位怎麼排，在 Streamlit 實作時決定。HTML 原型不重做。
- 不受影響的部分：三段分類的名稱與顏色、「不是警特報，也不表示降雨強度」的註記、取不到預報時顯示 UNKNOWN。
- 預報時段（審查處置的修正 4）：天氣表每一列保留採用的預報時段（起訖）與時段長度，表格下方固定說明降雨機率是預報時段的數值，不是抵達那一刻的預報（SPEC-001 第 4.8、5.5 與 7.13 節，草案）。路段對不到鄉鎮時顯示 UNKNOWN，不顯示低降雨機率。欄位在天氣表怎麼排，在 Streamlit 實作時決定；不重做原型。

停等寬放（審查處置 P-2；SPEC-RESOLUTION-001 採模型 M2）：畫面不顯示寬放的秒數，只在抵達時間旁顯示一句固定文字（第 8 節）。2026-11-14 被排除的那一趟行程維持排除（P-7），不影響畫面。

## 12. 新元素與 Streamlit 1.67.0 的對應

這張表接在 [UI_DESIGN](UI_DESIGN.md) 第 6 節的對照表之後。每一項都是標準元件；沒有地圖選點、拖曳、表格內編輯或只在滑鼠停留時出現的資訊。

| --- | --- | --- |
| Profile 區的容器 | `st.expander` | 原型沒有這個區塊。裡面不放另一個可展開區塊，所以處理進度放在它的外面 |
| 多檔選取歷史 GPX | `st.file_uploader`，`type` 限 gpx，`accept_multiple_files=True` | 原型沒有。元件本身也接受把檔案拖進去，但介面不依賴拖曳：按元件上的按鈕選檔就能完成 |

**原型和 CR-01 之後的介面不一致的地方。** 原型維持 G3 的版本，作為 G3 的紀錄。它的這些部分不再代表要做的介面：路線下拉選單；期限的固定名稱；搜尋狀態的標籤與「搜尋未完成」情境；候選的單選鈕與選取後的規則結果；「最接近時間限制的候選」的名稱；「已改用固定模板」的提示。回歸腳本 `prototype/g3-audit-check.js` 檢查的是 G3 的原型，不適用於 CR-01 之後的介面。

**沒有驗證的事。** 沒有建出 Streamlit 頁面。`st.file_uploader`、`st.radio` 與 `st.text_input` 不在 UI_DESIGN 第 6 節原本的對照表內；它們是 Streamlit 的標準輸入元件，但這次沒有重新對照 1.67.0 的官方文件。期限標籤切換時的行為如上表所述，尚未確認。`st.status` 能不能放進 `st.expander` 也沒有實測；這份文件的做法是不放進去，所以不依賴這一點。

## 13. 請專題負責人確認的事項

> 2026-11-15：UI-0 決策對照表的 22 項已由專題負責人確認（[ui0_decision_table.md](../cr/CR-01-appendix/ui0_decision_table.md)）：17 項照原文，U-1、U-7、U-14、U-16、U-22 修正後批准。下列第 2、4、6、7、10、11、12 項因此已確認（第 6 項指對照表涵蓋的文字）。UI-0 的畫面規格視為已確認；這不代表 SB-6、SB-10 或 SPEC-001 已經關閉。

1. **整份差異說明。** 以這份文件處理 CR-01 的介面變更，不重做原型，不重審 G3。
2. **行程型態是選填的表單欄位。** 有選時以表單為準；沒選時由行程描述判斷，再沒有就追問。另一個做法是改為必選，這樣就不會為了行程型態追問。CR-01 的文字同時提到「表單」與「追問」，這裡採用兩者都保留的讀法。
3. **路線確認區塊不擋住規劃（已裁決，審查處置 P-11）。** 它只顯示採用的路線，不增加強制的點擊。
4. **Profile 區的位置。** 放在 Trip Planner 上方的可展開區塊；驗收條件 A1 由「只有三個畫面」改為「三個畫面加上一個 Profile 區」。
5. **追問只有一輪。** 缺少的項目一次問完；回覆後仍無法決定路線時顯示路線錯誤。行程型態與休息方向在同一輪問（已裁決，2026-11-15）。
6. **固定文字的用字。** 路權提醒、配速資料涵蓋比例的句子、路線錯誤與評估失敗的訊息、Profile 的白話說明（第 3.3、6、7、8 節；SPEC-001 第 5.5 節）。SPEC-RESOLUTION-001 的裁決之後修正與新增的句子也在內：路權提醒、涵蓋比例、預設的餘裕係數、去程的高降雨機率提醒（第 6、8、10 節）。O-2 的裁決之後，「排不進去的休息」的訊息撤回；lead 依 O-2 寫的第七種路線錯誤的文字不採用。Q-1 的裁決之後新增兩則文字：休息對應不到地點時追問的固定模板，以及追問之後仍然對應不到時的表單訊息（第 5、7.1 節；SPEC-001 第 5.5 節）。Q-3 的裁決之後新增三則文字：無法確認折返點時的路線錯誤訊息，以及休息方向追問的模板與選項（第 5、7.1 節；SPEC-001 第 5.5 節）。Q-3 後續的裁決之後：無法確認折返點那一則的處理方式不指向特定的介面欄位；新增行程型態也在同一輪追問時方向那一題的標示「選擇來回時才需要回答」；「採用的條件」中休息策略的顯示文字（第 5、7.1、8 節；SPEC-001 第 5.5 節）。
7. **三個類別的白話名稱。** 低曲率（直路與緩彎）、中曲率（一般彎道）、高曲率（連續彎道）。
8. **F3 與 F4（已裁決，審查處置 P-11）。** Streamlit 的驗收保留基本的要求：375 像素寬度沒有整頁的水平溢出、可以用鍵盤操作（第 11.2 節）。
9. **目標路線 GPX 以文字欄輸入本機的檔案路徑。** 介面上傳維持 Should。選填的「折返位置（距起點的公里數）」欄位已裁決為 Should（2026-11-15；第 4 節）：折返位置先由 CLI 指定，這個欄位不是 UI-0 的要求，不需要在這裡確認。
10. **期限標籤的退路。** Streamlit 切換標籤時如果不保留已填的值，改用固定標籤「期限」加上欄位下方的名稱說明。
11. **代表性失敗候選的選法。** FAIL 的規則數最少；平手時取出發時間最晚的（第 9 節）。CR-01 第 11 節只裁決「簡化代表候選」，這個選法是文件定的。
12. **審查後新增的三處介面文字與位置。** 行程描述欄下方的說明（文字會送給語言模型）；去回里程差的提示；Profile 的處理進度放在可展開區塊之外。
