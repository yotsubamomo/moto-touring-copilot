## 1. 目的

CR-01 恢復了 Proposal 的核心體驗：歷史 GPX 的個人化配速、自然語言的行程描述、實際道路的路線、當天來回。這些改變集中在輸入的方式與路線的來源。三個畫面的結構、狀態標籤、UNKNOWN 的呈現與來源證據都不變。

這份文件做三件事：

1. 說明哪些內容維持凍結（第 2 節）。
2. 說明新增與修改的內容（第 3–8 節）、專題負責人接受的簡化（第 9 節）與還沒決定的部分（第 10 節）。
3. 對照到驗收條件與 Streamlit 1.67.0 的標準元件（第 11、12 節）。

沒有新一輪的需求討論，也沒有重新設計介面。

## 3. Profile 區（Must）

CR-01 的裁決 D1：歷史 GPX 的多檔介面上傳、合併去重複、Profile 更新與涵蓋度摘要是 Must，不能只做指令匯入；不得硬性要求至少五份 GPX。

這裡的 Profile 指由歷史 GPX 建立的個人配速表。Rider Profile 設定檔（油箱容量、平均油耗、休息習慣等）仍是靜態檔案，介面不提供編輯。

### 3.1 位置

頁首之下、Trip Planner 之上，一個可展開的區塊，標題是「騎士 Profile 與歷史 GPX」。還沒有配速表時預設展開，已經有配速表時預設收合。它不是第四個畫面，也不在分頁裡。

### 3.2 內容

| 內容 | 說明 | Streamlit 1.67.0 |
| --- | --- | --- |
| 涵蓋度摘要：三個數值 | 可用的行程數、可用的路段數、累計公里 | `st.metric` 三張 |
| 涵蓋度摘要：各類別的資料量 | 每個類別一列：類別、路段數、來自幾趟、資料夠不夠 | `st.table` |
| 白話說明 | 依資料量顯示其中一則，見 3.3 | `st.info` 或 `st.warning` |
| 選取歷史 GPX | 一次可以選多個檔案，只接受 `.gpx` | `st.file_uploader`（`accept_multiple_files=True`） |
| 「更新 Profile」按鈕 | 按下後才處理：合併到行程清單、以檔案內容去重複、重建配速表、更新摘要。合併的規則見表後 | `st.button` |
| 處理進度 | 步驟文字，不顯示百分比。顯示在 Profile 區的可展開區塊之外，緊接在它下方 | `st.status` |
| 處理結果 | 新增幾個檔案、略過幾個內容重複的檔案、幾個檔案無法讀取與原因 | `st.info`；有檔案無法讀取時用 `st.warning` |
| 隱私說明 | 固定文字，見 3.4 | `st.caption` |

類別沿用配速表的三類，介面寫成白話：低曲率（直路與緩彎）、中曲率（一般彎道）、高曲率（連續彎道）。

**合併的規則。** 行程清單是 `trip_id` 的唯一來源。新上傳的檔案以內容去重複後接續編號；已經指定的 `trip_id` 不變動，重複上傳、改檔名或改變上傳順序都不會讓既有的行程換編號。研究用的保留行程是以 `trip_id` 的清單凍結的，所以這一條不能違反（SPEC-001 第 2 節）。

### 3.3 資料少時的說法

沒有最少檔數的限制：一個檔案也可以更新 Profile。資料夠不夠只看每個類別的路段數有沒有達到配速表的最低要求（目前的暫行值是 30 段，定義在配速表的建立規則），不另外分級。摘要中的「來自幾趟」只用來顯示，不是資料夠不夠的條件。

| 情形 | 顯示的文字（提案） |
| --- | --- |
| 還沒有任何歷史 GPX | 還沒有歷史 GPX。沒有個人配速表時，系統無法估計抵達時間，和時間有關的規則會顯示 UNKNOWN。上傳一個檔案就可以開始。 |
| 某個類別的路段不夠 | 〈類別〉的路段還不夠（目前 N 段，需要 30 段）。路線含有這類路段時，系統無法估計抵達時間，會如實顯示 UNKNOWN。再上傳含有這類路段的行程就可以補上。 |
| 三個類別都夠 | 三個類別的資料都足夠估計。新的 GPX 可以隨時再加入。 |

資料不足時系統不以其他類別的數值代替（CR-01 第 6 節：缺類別時整條路線為 UNKNOWN 的規則保留）。

### 3.4 隱私

- 固定文字：「檔案只在這台電腦上處理與保存，不會送到任何外部服務。摘要只顯示彙總的數字。」
- 摘要不顯示座標、騎乘的日期與時間，也不顯示私有的路線名稱；不逐趟列出行程。
- 上傳元件本身會顯示剛選取的檔名，這是元件的行為。處理結果只在檔案無法讀取時列出檔名。
- 研究用的保留行程不進配速表（CR-01 第 13 節），也不計入摘要。
- 語言模型的 API 也是外部服務。歷史 GPX、逐趟的騎乘資料與住家位置不送給語言模型；送出去的只有通過本機輸入保護的行程文字（第 4 節）、結構化的條件，以及不含座標與軌跡點的工具輸出（SPEC-001 第 2 節）。

### 3.5 和規劃結果的關係

Profile 更新後配速表的版本改變。畫面上如果有舊的規劃結果，要標示為過期，直到再按一次「規劃」。更新 Profile 本身不會觸發規劃。

## 4. Trip Planner 的輸入區

路線下拉選單取消。路線改由行程描述或目標路線 GPX 決定。

| 欄位 | 必填 | 說明 | Streamlit 1.67.0 |
| --- | --- | --- | --- |
| 行程描述 | 沒有提供目標路線 GPX 時必填 | 一個自由文字欄。可以寫起點、目的地或公路、途經點、來回或單向，也可以補充休息與偏好。取代原本的「自然語言需求」欄。欄位下方固定說明（提案）：「這段文字會送給語言模型。請用公路或地標描述，不要寫住家地址或座標。系統會擋下常見的門牌與座標寫法，但無法保證擋下所有私人位置。」送出前在本機檢查：出現門牌或座標的寫法時不送出，在欄位下方顯示固定訊息，請騎士改寫；沒有「仍然送出」的選項（審查處置的修正 2；SPEC-001 第 7.12 節與第 5.5 節，草案） | `st.text_area` 加 `st.caption`；訊息用 `st.error` |
| 可用的公路與地標 | — | 公路與地標詞彙表中的名稱清單（先 5–8 條），讓騎士知道可以寫什麼。只列名稱，不列座標 | `st.expander` 內放 `st.table` |
| 日期 | 是 | 不變；可以選超出預報期間的日期 | `st.date_input` |
| 最早可出發時間 | 是 | 不變 | `st.time_input` |
| 期限 | 是 | 欄位的意義不變：路線終點的保守估計不得晚於它。名稱隨行程型態改變，見下方 | `st.time_input` |
| 出發油量 | 是 | 不變：0–100%，送出後程式再檢查一次 | `st.number_input` |
| 行程型態 | 否 | 「來回」或「單向」，預設不選。有選時以它為準；沒選時由行程描述判斷，再沒有就追問。來回指同一組起訖與途經點的去程與回程；回程由路線引擎另外算，走的道路可能和去程不完全相同 | `st.radio`（橫排，預設不選取） |
| 目標路線 GPX | 否 | 本機的檔案路徑。只讀路線的幾何，不讀時間。提供時路線以它為準 | `st.text_input` |
| Snapshot Mode | — | 不變。開啟時路線也只讀已保存的路線快照，不呼叫路線服務 | `st.checkbox` 或 `st.toggle` |
| 「規劃」按鈕 | — | 不變：唯一會觸發規劃的操作 | `st.button` |

**期限的兩個名稱。**

| 行程型態 | 欄位與結果中的名稱 |
| --- | --- |
| 來回 | 最晚回到出發點時間 |
| 單向 | 最晚抵達終點時間 |
| 還沒選 | 欄位標示為「期限」，下方說明「來回：最晚回到出發點的時間；單向：最晚抵達終點的時間」。規劃後，採用的條件使用上面兩個名稱之一 |

起點是出發錨點（代替住家的公開地標）時，期限欄位下方固定說明：「出發點不是住家；回到家的時間請自行加上。」起點是詞彙表中的其他公開地標時不顯示這一句。

目標路線 GPX 不會被系統推定為來回行程（審查處置的修正 3）。行程型態只來自表單、行程描述或追問。騎士指定來回時，還要明確指定折返點，或提供本身就是來回幾何的 GPX；兩者都沒有時不規劃，顯示路線錯誤，系統不自行補上回程（SPEC-001 第 7.11 節第 2 項）。這個錯誤的訊息文字待定（SB-7）。

**欄位檢查的變化。** 行程描述與目標路線 GPX 都沒有提供時不進入規劃，錯誤摘要與欄位旁的錯誤照 G3 的做法顯示。其他檢查不變。

**衝突的處理不變。** 行程描述和表單不一致時以表單為準，並在結果中提示。CR-01 之後會發生衝突的欄位是行程型態、日期、時間、油量；另外，行程描述寫了路線、同時又提供目標路線 GPX 時，以 GPX 為準並提示。

**目標路線 GPX 的介面上傳是 Should**，不在這次的 Must。做的時候用單檔的 `st.file_uploader`，取代檔案路徑的文字欄。

## 5. 追問

追問仍然只在缺少必要條件或有歧義時出現，位置不變（規劃進度的下方）。

| 項目 | G3 | CR-01 之後 |
| --- | --- | --- |
| 追問的主題 | 休息安排有歧義 | 缺起點；不知道從公路的哪一端進；沒說來回或單向；休息多久 |
| 一次問幾題 | 一題 | 把缺少的項目一次列在同一個區塊，每一題一組選項 |
| 選項的來源 | 固定選項 | 起點與進入端的選項只來自詞彙表與 Rider Profile；行程型態是來回或單向；休息長度是固定選項 |
| 回覆 | 選取後按回覆 | 全部選完後按一次「回覆並繼續規劃」 |
| 輪數 | 一輪 | 一輪。回覆後仍無法決定路線時顯示路線錯誤（第 7 節），不再追問 |

這不是聊天：沒有對話輸入框，沒有多輪往返，結果產生後也沒有自由對話（UI_ACCEPTANCE A2 不變）。

Streamlit 的做法：一個 `st.chat_message` 區塊說明缺少什麼，裡面每一題一個 `st.radio` 或 `st.selectbox`，最後一個 `st.button`。不使用 `st.chat_input`。

## 6. 路線確認區塊

路線取得之後顯示，位置在追問之下、結果過期的提示之上。兩個分頁都看得到它。它讓騎士確認系統採用的是哪一條路；它不是按鈕，不擋住規劃，也不增加強制的點擊（審查處置 P-11）。騎士不同意這條路線時，修改行程描述後再按一次「規劃」。

| 內容 | 說明 | Streamlit 1.67.0 |
| --- | --- | --- |
| 行程型態與起訖 | 來回或單向；起點、目的地或公路、途經點的名稱 | 文字 |
| 里程 | 整條路線的公里數；來回行程包含回程 | `st.metric` |
| 主要道路名稱 | 依行經順序列出。只有名稱，沒有座標，沒有地圖 | 文字清單 |
| 路線來源的標籤 | 「路線引擎」「目標路線 GPX」「示範路線」三者之一，灰色 | `st.badge` |
| 路線快照的標籤 | 路線來自路線快照時顯示「資料快照」（藍色），附快照的時間 | `st.badge` 加文字 |
| 去回里程差的提示 | 只在來回行程的去程與回程里程相差超過 2% 時顯示（`route.leg_length_diff_flag`）。固定句子，見下方 | `st.info` |
| 路權提醒 | 固定句子，見下方 | `st.caption` 或 `st.info` |

整個區塊放在 `st.container(border=True)` 裡。

**固定句子**（提案；文字與 SPEC-001 第 5.5 節相同，不由語言模型產生）：

- 路線來自路線引擎時：「這條路線由路線引擎依開放圖資產生，已檢查不含國道。其他道路的機車通行限制（例如部分快速公路與高架道路）系統無法保證，請出發前自行確認路權。」
- 路線來自目標路線 GPX 或示範路線時：「這條路線取自你提供的 GPX 或騎過的行程。系統沒有檢查國道與機車通行限制，請出發前自行確認路權。」
- 去回里程差超過 2% 時：「回程是另外算的路線，和去程的里程相差約 N%，走的道路不完全相同。請查看道路名稱。」

「已檢查不含國道」指的是系統自己做的獨立國道檢查，每個方向都通過才採用這條路線（SPEC-001 第 7.11 節）。句子不寫「已排除」：路線參數是 `use_highways: 0`（審查處置 P-1），它是偏好，不是保證；保證來自獨立的國道檢查。這個設定可能連快速公路也避開，路線會比較慢。

路線引擎回報的行駛時間不顯示，避免和個人的典型估計、保守估計混淆。

## 7. 路線錯誤與評估失敗

CR-01 的裁決 D2：路線服務失敗時不得讓語言模型編造路線，必須有驗證過的快照或明確的錯誤處理。

### 7.1 路線錯誤

出現的情形與畫面上的文字（提案；與 SPEC-001 第 5.5 節相同）：

| 情形 | 錯誤訊息 | 騎士可以怎麼做 |
| --- | --- | --- |
| 行程描述中的公路或地標不在詞彙表內 | 行程描述中的「〈名稱〉」不在目前支援的公路與地標清單內，系統沒有產生路線。 | 改用清單內的公路或地標重新描述；或提供目標路線 GPX。 |
| 路線服務沒有回應、回傳錯誤，或找不到可用的路線 | 路線服務沒有回傳可用的路線，系統沒有產生路線。 | 稍後再按一次「規劃」；改用 Snapshot Mode 規劃已有快照的行程；或提供目標路線 GPX。 |
| 回傳的路線沒有通過獨立的國道檢查 | 路線服務回傳的路線沒有通過國道檢查，系統不採用這條路線。 | 增加途經點讓路線避開國道；或提供目標路線 GPX。 |
| Snapshot Mode 下沒有對應的路線快照 | Snapshot Mode 只使用已保存的路線快照，這個行程沒有對應的快照。 | 關閉 Snapshot Mode 後重新規劃；或改成有快照的行程。 |
| 目標路線 GPX 無法使用 | 目標路線 GPX 無法當成路線使用：讀不到軌跡點，或點與點之間的距離太遠。 | 確認檔案路徑與內容；改用記錄較密的 GPX；或改用行程描述。 |

兩點說明：

- 一般模式下路線服務失敗時，系統不會自動改用舊的路線快照；只有騎士自己開啟 Snapshot Mode 才讀已保存的快照。
- 路線參數是 `use_highways: 0`（審查處置 P-1）。回應帶有任何警告時不採用這條路線，顯示 `routing_unavailable` 的訊息（SPEC-001 第 4.13 節與第 7.11 節第 7 項）。

畫面：

- 路線確認區塊的位置改顯示錯誤訊息與「可以怎麼做」的清單（`st.error` 加文字清單）。
- 不顯示計畫狀態標籤、出發時間與任何路線的里程或道路名稱。
- 兩個分頁顯示「沒有可用的路線，尚未規劃」。
- 仍顯示採用的條件（騎士輸入的內容）。

### 7.2 評估失敗

候選的評估因為程式錯誤或中止而沒有完成時：

- 顯示固定訊息（提案；與 SPEC-001 第 5.5 節相同）：候選的評估沒有完成，這次不提供建議的出發時間。請再按一次「規劃」；仍然失敗時，改用 Snapshot Mode 或稍後再試。
- 不顯示計畫狀態標籤，不顯示建議的出發時間，不出現「最晚的可行出發時間」，也不說無可行解。
- 路線確認區塊、採用的條件與來源證據照常顯示。

工具回傳 UNKNOWN 不算評估失敗；那種情形照 G3 的做法顯示 UNKNOWN 與待確認事項。

### 7.3 三種錯誤共用一個版面

路線錯誤、評估失敗與輸出驗證錯誤的版面相同：一則錯誤訊息、可以怎麼做、沒有計畫狀態標籤，仍顯示採用的條件與現有的來源證據。差別只在訊息的內容，以及路線錯誤時沒有路線確認區塊。

## 10. 待裁決：來回行程的天氣呈現

規則 3 在來回行程上的範圍還沒有決定（CR-01 的 D3）。專題負責人不接受「整個回程遇到高降雨機率提醒就 FAIL」，要求比較「回程全部路段」與「山區回程路段」兩種範圍後再定。審查處置 P-8：暫不採用曲率或固定高度的定義；lead 在 11/27 前提出最小方案，由專題負責人定案，最晚 2026-12-03（SPEC-001 第 11.1 節）。

在那之前：

- 單向行程的天氣表不變：前段、中段與最後 20% 三列。
- 來回行程的天氣表怎麼分列、哪幾列標示為規則 3 的範圍，**等 D3 定案後再寫**。這份文件不提出暫定的版面。
- 不受影響的部分：三段分類的名稱與顏色、「不是警特報，也不表示降雨強度」的註記、取不到預報時顯示 UNKNOWN。
- 預報時段（審查處置的修正 4）：天氣表每一列保留採用的預報時段（起訖）與時段長度，表格下方固定說明降雨機率是預報時段的數值，不是抵達那一刻的預報（SPEC-001 第 4.8、5.5 與 7.13 節，草案）。路段對不到鄉鎮時顯示 UNKNOWN，不顯示低降雨機率。欄位在天氣表怎麼排，在 Streamlit 實作時決定；不重做原型。

停等寬放已由審查處置 P-2 升為 Must；要不要在畫面上說明寬放的量，等它的定義確定後再決定（SPEC-001 第 11.1 節 SB-2）。2026-11-14 被排除的那一趟行程維持排除（P-7），不影響畫面。

## 12. 新元素與 Streamlit 1.67.0 的對應

這張表接在 [UI_DESIGN](UI_DESIGN.md) 第 6 節的對照表之後。每一項都是標準元件；沒有地圖選點、拖曳、表格內編輯或只在滑鼠停留時出現的資訊。

| 新元素 | Streamlit 1.67.0 | 和原型的差異、限制 |
| --- | --- | --- |
| Profile 區的容器 | `st.expander` | 原型沒有這個區塊。裡面不放另一個可展開區塊，所以處理進度放在它的外面 |
| 多檔選取歷史 GPX | `st.file_uploader`，`type` 限 gpx，`accept_multiple_files=True` | 原型沒有。元件本身也接受把檔案拖進去，但介面不依賴拖曳：按元件上的按鈕選檔就能完成 |
| 更新 Profile | `st.button` | 原型沒有。放在表單之外 |
| Profile 的處理進度 | `st.status`，放在 Profile 區的 `st.expander` 之外、緊接在它下方 | 原型沒有。顯示步驟文字，不顯示百分比。`st.status` 本身是可展開的容器，放進 `st.expander` 會成為巢狀的可展開區塊，所以不放在裡面 |
| 涵蓋度的三個數值 | `st.metric` | 原型沒有 |
| 各類別的資料量 | `st.table` | 原型沒有 |
| 資料量的白話說明、處理結果 | `st.info`、`st.warning` | 原型沒有。不用綠色的成功提示，綠色保留給 PASS 與 FEASIBLE |
| 行程描述 | `st.text_area`，下方一則 `st.caption` | 原型的同一個位置是「自然語言需求」。說明文字提醒這段文字會送給語言模型 |
| 可用的公路與地標 | `st.expander` 內放 `st.table` | 原型沒有 |
| 行程型態 | `st.radio`（橫排，`index=None`） | 原型沒有 |
| 期限的名稱隨行程型態改變 | `st.time_input` 的標籤由 session state 決定 | 原型的名稱固定是「最晚抵達終點時間」。標籤改變時欄位已填的值會不會保留，要在實作時確認；不保留時改用固定的標籤「期限」，名稱寫在欄位下方的 `st.caption` |
| 目標路線 GPX 的檔案路徑 | `st.text_input` | 原型沒有。路徑與檔名只在本機使用，不寫進結果；結果只記錄檔案的內容雜湊 |
| 追問區塊（多題） | `st.chat_message` 內放每題一個 `st.radio` 或 `st.selectbox`，加一個 `st.button` | 原型的追問只有一題。不使用 `st.chat_input` |
| 路線確認區塊 | `st.container(border=True)` 內放 `st.badge`、`st.metric`、文字與 `st.caption` | 原型沒有。沒有地圖 |
| 去回里程差的提示 | `st.info` | 原型沒有。只在里程相差超過 2% 時顯示 |
| 路線錯誤、評估失敗 | `st.error` 加文字清單 | 原型只有輸出驗證錯誤的版面，三者共用 |
| 路線摘要、配速資料涵蓋比例的句子 | 文字、`st.info` | 原型沒有 |
| Planner 的補充說明 | 文字加 `st.caption` 標示來源 | 原型以提示框說明「已改用固定模板」，不再需要 |
| 全部候選（唯讀） | `st.expander` 內放 `st.dataframe`，不開啟列的選取 | 原型有單選鈕與選取後的規則結果，不再需要 |

**原型和 CR-01 之後的介面不一致的地方。** 原型維持 G3 的版本，作為 G3 的紀錄。它的這些部分不再代表要做的介面：路線下拉選單；期限的固定名稱；搜尋狀態的標籤與「搜尋未完成」情境；候選的單選鈕與選取後的規則結果；「最接近時間限制的候選」的名稱；「已改用固定模板」的提示。回歸腳本 `prototype/g3-audit-check.js` 檢查的是 G3 的原型，不適用於 CR-01 之後的介面。

**沒有驗證的事。** 沒有建出 Streamlit 頁面。`st.file_uploader`、`st.radio` 與 `st.text_input` 不在 UI_DESIGN 第 6 節原本的對照表內；它們是 Streamlit 的標準輸入元件，但這次沒有重新對照 1.67.0 的官方文件。期限標籤切換時的行為如上表所述，尚未確認。`st.status` 能不能放進 `st.expander` 也沒有實測；這份文件的做法是不放進去，所以不依賴這一點。

## 13. 請專題負責人確認的事項

1. **整份差異說明。** 以這份文件處理 CR-01 的介面變更，不重做原型，不重審 G3。
2. **行程型態是選填的表單欄位。** 有選時以表單為準；沒選時由行程描述判斷，再沒有就追問。另一個做法是改為必選，這樣就不會為了行程型態追問。CR-01 的文字同時提到「表單」與「追問」，這裡採用兩者都保留的讀法。
3. **路線確認區塊不擋住規劃（已裁決，審查處置 P-11）。** 它只顯示採用的路線，不增加強制的點擊。
4. **Profile 區的位置。** 放在 Trip Planner 上方的可展開區塊；驗收條件 A1 由「只有三個畫面」改為「三個畫面加上一個 Profile 區」。
5. **追問只有一輪。** 缺少的項目一次問完；回覆後仍無法決定路線時顯示路線錯誤。
6. **固定文字的用字。** 路權提醒、配速資料涵蓋比例的句子、路線錯誤與評估失敗的訊息、Profile 的白話說明（第 3.3、6、7、8 節；SPEC-001 第 5.5 節）。
7. **三個類別的白話名稱。** 低曲率（直路與緩彎）、中曲率（一般彎道）、高曲率（連續彎道）。
8. **F3 與 F4（已裁決，審查處置 P-11）。** Streamlit 的驗收保留基本的要求：375 像素寬度沒有整頁的水平溢出、可以用鍵盤操作（第 11.2 節）。
9. **目標路線 GPX 以文字欄輸入本機的檔案路徑。** 介面上傳維持 Should。
10. **期限標籤的退路。** Streamlit 切換標籤時如果不保留已填的值，改用固定標籤「期限」加上欄位下方的名稱說明。
11. **代表性失敗候選的選法。** FAIL 的規則數最少；平手時取出發時間最晚的（第 9 節）。CR-01 第 11 節只裁決「簡化代表候選」，這個選法是文件定的。
12. **審查後新增的三處介面文字與位置。** 行程描述欄下方的說明（文字會送給語言模型）；去回里程差的提示；Profile 的處理進度放在可展開區塊之外。
