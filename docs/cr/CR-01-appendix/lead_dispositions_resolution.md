### 5.1 O-1：E2 規則 3 的 Oracle（修正後批准）

裁決：不接受「把完整策略寫入題目」作為唯一的解法。規則 3 的 Oracle 可以用「整個候選抵達時間範圍內分類不變」的預報情境獨立判定。跨預報時段的案例若要正式計分，Oracle 要用凍結的輸入與獨立實作的 ETA 算式，不得匯入 production 的 `pace`、Validator 或 Planner。以合成案例與人工驗算確認 Oracle。沒有實作時間相依的 Oracle 時，E2 不得宣稱已驗證跨預報時段的正確對齊。

定案內容：

| 項目 | 規則 |
| --- | --- |
| 兩類題目 | **時間不變題**：在題目的候選抵達時間範圍（最早可出發時間到期限）內，規則 3 範圍內每個路段所對應的鄉鎮，各預報時段的降雨機率分類都相同（或都缺）。**跨時段題**：不符合上述條件的題目 |
| 時間不變題的判定 | Oracle 只用凍結的預報、凍結快照的折返點與路段、題庫紀錄中的路段對應鄉鎮（題庫凍結時產生並人工核對）、定案的範圍。結果和出發時間、配速表、餘裕係數無關。判定規則和 SPEC-RESOLUTION-001 3.1 相同 |
| 跨時段題的判定 | 只有在實作了時間相依的 Oracle 時才正式計分。時間相依的 Oracle 以凍結的輸入（凍結的研究用配速表的數值、凍結的路線、題目的出發時間）與**獨立實作**的 ETA 算式計算抵達時段；算式依 DESIGN §6.1 重寫，不匯入 `pace`、Validator、Planner 或任何 production 的程式 |
| 沒有實作時間相依的 Oracle 時 | 跨時段題不出題，或出題但不計分並標明。E2 的報告不得宣稱已驗證跨預報時段的正確對齊 |
| Oracle 的確認 | 兩種 Oracle 都以合成案例確認：每種結果（PASS、FAIL、UNKNOWN）至少一個案例，預期值由人工驗算並寫入題庫紀錄。時間相依的 Oracle 另以人工驗算至少一題的抵達時段 |
| 三組的任務說明 | 三組收到相同的任務說明。任務說明是否列出規則 3 的定義，在題庫凍結前寫進 E2 的規格，三組一致 |

### 5.2 O-2：騎士指定的休息（批准，附加條件）

裁決：路線上已確認的指定途經點建立為 `waypoint` 檢查點。騎士明確要求的休息無法安排時，必須由確定性的程式回報，不能依賴語言模型自己發現。沒有把指定休息納入 ETA 的計畫，不得作為已滿足條件的有效計畫。

定案內容：

| 項目 | 規則 |
| --- | --- |
| 途經點的檢查點 | 每個指定的途經點，偏移檢查通過（≤ 200 m）後，在離它最近的路段邊界建立一個 `kind = waypoint` 的檢查點（契約 2 既有的種類），名稱是地標的名稱。來回行程的去程與回程各建立一個 |
| 可以排休息的檢查點 | `waypoint`、`fuel_station`、`turnaround`。起點與終點不排 |
| 確定性的檢查一 | 主程式檢查 Planner 給的每一筆休息：`after_checkpoint_id` 必須是這條路線上可以排休息的檢查點。不是時，這一筆算「排不進去」 |
| 確定性的檢查二 | 主程式以固定的關鍵詞清單檢查行程描述（「休息」「用餐」「吃飯」「午餐」「晚餐」「拍照」「停留」；清單寫在設定檔）。描述含關鍵詞，而 Planner 的輸出沒有任何 `origin = free_text` 的休息時，算「排不進去」。這個檢查不經過語言模型 |

| --- | --- | --- | --- |

### 5.4 O-4：模擬預報的題目（有條件批准）

- 模擬預報的題目計入正式的 12–15 題，最多 3 題。
- 人工移除預報來製造 UNKNOWN，也計入這 3 題。真實來源本身缺漏（例如日期超出預報涵蓋區間）不算人工模擬。
- 題庫凍結時預先定義三個數：`N_total`（全部正式題目，12–15）、`N_weather_real`（預報沒有經過人工修改的題目）、`N_weather_sim`（預報經過人工修改或移除的題目，≤ 3）。`N_total = N_weather_real + N_weather_sim`。
- H2 的主要指標以 `N_weather_real` 的題目計算。全部題目的結果與模擬預報題的結果另外報告。
- 樣本不足時標記「證據有限」：任何指標的分母少於 5 題時標記（5 是提案的數值）。

### 5.5 O-5：方案 A 與方案 B 的敏感度分析（批准）

- 對來回行程的題目，以完全相同的凍結資料，分別用方案 A（整段回程）與方案 B（路線最後 20%）判定規則 3。
- 分開報告兩個數：(1)「額外的規則 3 FAIL」：方案 A 是 FAIL、方案 B 不是 FAIL 的題數；(2)「因規則 3 的差異而使整體計畫由可行轉為不可行」的題數：預期狀態在方案 B 之下是 `FEASIBLE` 或 `CONDITIONAL`、在方案 A 之下是 `INFEASIBLE`。
- 這是敏感度分析，不稱為 Over-refusal Rate，也不推論額外的拒絕是否不合理。
- E2 原本的 Over-refusal Rate 與它的定義不變。
- 由 Oracle 在題庫凍結時算出；跨時段題只有在實作了時間相依的 Oracle 時才納入，否則註明未納入。

## 8. Q-3 七項的裁決（2026-11-15，專題負責人）與定案內容

七項已逐項裁決。項次和 [q3_derived_details.md](q3_derived_details.md) 相同。這一節取代第 5.6、6.3、7.1（第 5 項中「來回行程取去程的那一個」）與 7.6 節中和它不同的地方。沒有重跑審查。

「lead 寫定」標示的是裁決沒有寫、為了讓規則可以實作而補上的最小內容。

### 8.1 第 1 項：快照與 ID（有條件批准）

裁決：接受不可變的快照，以及 `SN-`／`RS-`／`RG-` 與 `checkpoint_id` 的格式。快照由正規化後的內容產生代號；內容完全相同就重用，內容不同就建立新的快照，不覆寫舊的。雜湊的正規化要修正：經緯度至少保留小數六位，不得把全部浮點數統一取小數一位。新路線快照的 `route_id` 可以改變；既有已保存的結果仍然指向原來的快照，不能默默替換。

| 編號 | 規則 |
| --- | --- |
| 1 | 格式不變：`snapshot_id` 是 `SN-` 加 10 個小寫十六進位字元；路線引擎路線的 `route_id` 是 `RS-` 加同一組字元；目標 GPX 的 `route_id` 是 `RG-` 加 10 個字元；`checkpoint_id` 是 `<route_id>-CP` 加兩到三位數字；`trip_id` 與 `R01`／`R02` 不變 |
| 2 | 代號取自正規化後的快照內容的 SHA-256 前 10 碼。**雜湊的範圍不含 `snapshot_id` 本身與各方向的取得時間（`fetched_at`）**（lead 寫定：取得時間每次都不同，含在內就永遠不會「內容完全相同」） |
| 3 | 重新取得後內容完全相同：代號相同，沿用既有的檔案，不寫入、不修改。內容不同：新的代號、新的檔案，舊檔不動。以既有的代號寫入不同的內容時報錯 |
| 4 | 正規化：UTF-8 的 JSON，鍵依字典順序，沒有多餘的空白；**經緯度取小數六位**；以公尺計的長度與偏移取小數一位；其他浮點數取小數六位（後兩句是 lead 寫定）；時間用 SPEC 第 2 節的格式。`request_key` 用同一套規則 |
| 5 | 新的快照有新的 `route_id`。已保存的結果繼續記錄並顯示它當時使用的 `route_id` 與 `snapshot_id`，不會被改指到新的快照；要用新的快照就重新規劃，得到新的結果 |
| 6 | 目標 GPX 的 `RG-` 代號：雜湊的輸入是檔案內容的 SHA-256、`trip_type`，以及指定的折返位置（換算成公尺的整數；沒有指定時不含）。同一個檔案指定不同的折返位置會切出不同的路段，必須是不同的 `route_id`（lead 寫定；8.2 允許指定折返位置之後才需要，待專題負責人確認） |

後果（要讓專題負責人知道）：既有快照的取得時間不會更新。同一條路超過 30 天之後，一般模式每次規劃都會重新向路線引擎取得；內容沒有變時沿用舊檔，不產生新檔。

測試：Q3-T1 同一份內容、不同的取得時間得到同一個 `snapshot_id`，檔案沒有被改寫；Q3-T2 折線或任何其他內容不同時是新的代號，舊檔的內容不變；Q3-T3 以既有的代號寫入不同的內容會報錯；Q3-T4 經緯度第六位小數不同的兩份內容得到不同的雜湊，第七位以後不同的得到相同的雜湊；Q3-T5 重新取得並產生新快照之後，已保存結果的 `route_id` 與 `snapshot_id` 不變；Q3-T6 所有代號符合樣式。另外需要一項：同一個 GPX 檔指定兩個不同的折返位置得到兩個不同的 `route_id`（隨第 6 項確認後加入）。

### 8.2 第 2 項：目標 GPX（修改）

裁決：保留「必須明確指定來回，而且 GPX 的幾何包含回到起點」的條件。只有明確去回同路、折返點沒有歧義時，才自動取離起點最遠的軌跡點。環狀或 8 字形等有歧義的 GPX 不得默默推定折返點；允許指定軌跡上的折返位置，無法確認就回報。不反轉、不補造回程，保持最小的 CLI 規格。

| 編號 | 規則 |
| --- | --- |
| 1 | 來回的條件不變：騎士明確指定來回，而且 GPX 的終點回到起點（相距 200 m 以內）。不符合時回傳 `target_gpx_not_round_trip` |
| 2 | 去回同路的判定（lead 寫定判定方式與數值）：先以離起點直線距離最遠的軌跡點把軌跡分成前後兩段；後段每 100 m 取一點，取樣點 50 m 內有前段的軌跡點算接近。接近的取樣點達 **90%** 以上時算「明確去回同路」，自動以那個最遠點為折返點。50 m 與 100 m 沿用路線接近比例的設定；90% 是提案的數值 |
| 3 | 沒有達到第 2 項的條件時（環狀、8 字形或其他有歧義的幾何），不自動推定。騎士可以指定折返位置：**距離起點的軌跡里程，以公里表示**（lead 寫定輸入方式；地標在環狀路線上可能經過兩次，里程不會有歧義）。指定的里程必須大於 0、小於軌跡總長 |
| 4 | 有歧義而騎士沒有指定折返位置，或指定的里程不合法時：不規劃，回傳 `target_gpx_not_round_trip`，訊息說明無法確認折返點，請指定折返位置或改選單向。不新增錯誤代碼 |
| 5 | 在折返點切開，去程與回程分開切段。不反轉、不補造回程 |
| 6 | 介面：目標路線 GPX 的路徑欄位旁加一個選填的數字欄位「折返位置（距起點的公里數）」，只在指定來回時使用（lead 寫定） |

測試：Q3-T7 去回同路的 GPX 自動取最遠點；Q3-T8 環狀的 GPX 沒有指定折返位置時回傳 `target_gpx_not_round_trip`，沒有計畫；Q3-T9 環狀的 GPX 指定折返位置後以那個位置切開；Q3-T10 指定的里程是 0、負數或超過總長時回報；Q3-T11 終點沒有回到起點時，即使指定了折返位置也回傳 `target_gpx_not_round_trip`；Q3-T12 任何情形下都沒有反轉或補造的軌跡點。

### 8.3 第 3 項：指定的休息（部分批准）

裁決：接受既有的一次追問，追問之後仍然無法安排時不產生有效的計畫。不能一律把來回行程途經點的休息排在去程：有明確的方向時依方向安排；去程與回程都有那個地點而方向不明時，用既有的追問確認。使用者指定的休息不可被重新規劃移除、搬移或縮短。不新增第七個路線錯誤代碼，也不恢復關鍵詞檢查。

| 編號 | 規則 |
| --- | --- |
| 1 | 休息需求多一個方向：`direction`，值是 `outbound`、`return` 或空（lead 寫定欄位名稱）。行程描述寫明去程或回程時由 Planner 填入 |
| 2 | 來回行程、地點是指定的途經點：有方向時對到那個方向的 `waypoint` 檢查點。方向是空的時候，放進既有的那一次追問，選項是「去程」「回程」「不安排這段休息」 |
| 3 | 地點是折返點，或行程是單向：不需要方向 |
| 4 | 追問之後仍然對應不到時不產生計畫，由表單的檢查擋下（7.1 第 4 項，已接受） |
| 5 | 重新規劃不得移除、搬移或縮短來源是 `free_text` 或 `clarification` 的休息（7.1 第 7 項，不變） |
| 6 | 路線錯誤代碼維持六個；沒有關鍵詞檢查 |

7.1 第 5 項的「來回行程取去程的那一個」作廢。

測試：Q3-T13 行程描述寫明「回程在某途經點休息」：對到回程的 `waypoint` 檢查點；Q3-T14 來回行程、途經點的休息沒有方向：追問的選項是去程、回程、不安排，沒有計畫；Q3-T15 回覆「回程」後對到回程的檢查點並計入 ETA。Q1-T1 改為單向行程或已指明方向的情形。

### 8.4 第 4 項：`via_offset_m`（批准）

裁決：記錄每個中間位置的偏移，包含指定的途經點與公路的進入端；保留 200 m 的門檻；增加依路線行進順序驗證途經點的測試，避免靠近但沒有依序經過。

| 編號 | 規則 |
| --- | --- |
| 1 | `via_offset_m` 依送給引擎的中間位置的順序，記錄每個位置到折線最近點的距離。任何一個超過 200 m 時不採用，回傳 `routing_unavailable` |
| 2 | 順序：每個中間位置在折線上最近點的沿線里程，必須依請求的順序遞增。不符合時不採用，回傳 `routing_unavailable`（順序的判定方式是 lead 依裁決的測試要求寫定） |

測試：Q3-T16 途經點離折線超過 200 m 時拒收；Q3-T17 兩個途經點都在 200 m 內、但折線經過它們的順序和請求相反時拒收；Q3-T18 公路的進入端也有偏移紀錄。

### 8.5 第 5 項：`request_key`（有條件批准）

裁決：使用地標代號加座標定義的 SHA-256 指紋，不使用整份詞彙表的版本。指紋建議取前 16 碼；確認經緯度的正規化精度。增加「地標座標改變」與「未引用的地標改變」的測試。

| 編號 | 規則 |
| --- | --- |
| 1 | `request_key` 中每個地點是「代號加指紋」。指紋是該地標座標定義的 SHA-256 **前 16 碼**；座標先正規化為小數六位（8.1 第 4 項） |
| 2 | 鍵裡沒有座標本身。只有被引用的地標改過，才算不同的請求 |

測試：Q3-T19 被引用地標的座標在第六位小數以內改變時 `request_key` 改變；Q3-T20 沒有被引用的地標改變時 `request_key` 不變；Q3-T21 途經點的順序對調時 `request_key` 改變。

### 8.6 第 6 項：Snapshot Mode（修改）

裁決：一般的 Snapshot Mode 使用最近且相容的已保存快照。E2 與凍結的 Demo 嚴格採用凍結清單指定的 `snapshot_id` 與檔案的 SHA-256；不存在或驗證失敗就停止，不回退到最新的快照。`freeway_check_method` 不相容時不得採用。加入「凍結清單優先」「雜湊失敗」「檢查方法不相容」的測試。

| 編號 | 規則 |
| --- | --- |
| 1 | 一般的 Snapshot Mode：用 `request_key` 相同、`freeway_check_method` 和現行方法相同的已保存快照中，取得時間最晚的一個。沒有時回傳 `snapshot_missing` |
| 2 | 嚴格模式：執行時指定了凍結清單（E2 的 Runner 與凍結的 Demo）。只採用清單指定的 `snapshot_id`，並核對檔案的 SHA-256。檔案不存在或雜湊不符時停止執行，不回退到任何其他快照。「指定了凍結清單就是嚴格模式」是 lead 寫定的觸發方式 |
| 3 | 兩種模式下，`freeway_check_method` 和現行方法不同的快照都不採用。嚴格模式下遇到這種情形同樣停止 |
| 4 | 檢查方法在 E2 凍結之後不得更改 |

測試：Q3-T22 有凍結清單時採用清單指定的快照，即使有取得時間更晚的快照；Q3-T23 清單指定的檔案不存在或 SHA-256 不符時停止，沒有回退；Q3-T24 檢查方法不同的快照在兩種模式下都不採用；Q3-T25 一般的 Snapshot Mode 取相容的快照中取得時間最晚的一個。

## 9. Q-3 後續九項的裁決（2026-11-15，專題負責人）與定案內容

第 8.8 節留下的九個小規則（A、B1–B3、C1–C5）與兩件附帶的事已裁決。這一節取代第 8 節中和它不同的地方。沒有重跑審查。

### 9.1 A：目標 GPX 的 `route_id`（批准）

`RG-` 的 `route_id` 必須包含**實際採用的折返位置**（距起點的累計公尺，整數），不論它是自動判定還是騎士指定的。相同的幾何、相同的有效折返點得到相同的 `route_id`；不同的折返點得到不同的 `route_id`。

雜湊的輸入：檔案內容的 SHA-256（十六進位字串）、一個冒號、`trip_type` 的值；來回行程再接一個冒號與實際採用的折返位置（公尺的整數）。單向行程沒有折返位置這一段。取 SHA-256 的前 10 碼。

測試：Q3-T26 同一個檔案，自動判定的折返位置和騎士指定的折返位置相同（換算成公尺後相等）時 `route_id` 相同；折返位置不同時 `route_id` 不同；同一個檔案的單向與來回 `route_id` 不同。

### 9.2 B1：去回同路的自動辨識（有條件批准）

50 m／100 m／90% 是 MVP 自動辨識的**保守啟發式門檻**。它沒有以真實資料驗證過，文件與報告都不得這樣宣稱。辨識不明確時交給騎士指定，不默默猜測。

測試（合成資料）：Q3-T27 四種形狀各一個案例：去回同路（自動取最遠點）；環狀；8 字形；重合比例不足（例如去程與回程只有一部分同路）。後三種都不自動推定，沒有指定折返位置時回傳 `target_gpx_not_round_trip`。

### 9.3 B2：折返位置的輸入（批准）

折返位置以「距起點的軌跡公里數」輸入，換算成公尺後使用。**先由 CLI 支援。** 目標 GPX 的介面上傳仍是 Should；介面上選填的折返欄位也是 Should，**不是 UI-0 的 Must，不得擋住 UI Gate**。介面沒有這個欄位時，有歧義的 GPX 在介面上只會得到 `target_gpx_not_round_trip` 的訊息。

### 9.4 B3：指定與自動的優先順序（批准）

騎士明確指定的合法折返位置優先於自動判定。其他條件不變：GPX 的終點必須回到起點（200 m 以內）；不反轉、不補造回程。

測試：Q3-T28 明確去回同路的軌跡上，騎士指定了另一個合法的折返位置：以騎士指定的為準。

### 9.5 C1：`waypoint` 檢查點（批准）

檢查點依行經的順序編號；同一個位置有多個檢查點時加油站在前。`waypoint` 不當作 `fuel_station`，也不直接加入 FuelPlan 的檢查點。

測試：Q3-T29 同一個路段邊界同時有加油站與途經點時，加油站的編號在前；FuelPlan 的檢查點清單沒有 `waypoint`。

### 9.6 C2：兩種「不休息」的意圖（修正原建議）

- 騎士明確選擇**整趟不安排休息**：不套用 Rider Profile 的預設休息。
- 在追問中取消某一筆或全部的個別休息需求：不自動解讀成整趟禁止預設休息。取消之後沒有任何休息安排時，預設休息照常套用。
- 兩種意圖在結構化的條件中區分，不用關鍵詞猜測。

做法：規劃請求多一個欄位 `rest_policy`（欄位名稱是 lead 定的），值是 `default`（沒有特別指定，預設休息的規則照常適用）或 `none`（整趟不安排休息）。它由 Planner 從行程描述轉成結構化資料，或由追問的回覆填入；結果的「採用的條件」會顯示它。追問中的「不安排這段休息」只取消那一筆需求，不改變 `rest_policy`。

測試：Q3-T30 `rest_policy = none` 時結果沒有任何來源是 `rider_profile` 的休息；Q3-T31 追問中取消了全部的個別休息需求、`rest_policy = default` 時，預設休息照常排入。

### 9.7 C3：重新規劃與加油停留（批准）

重新規劃可以調整系統自動安排的加油停留，包含第一次規劃排的與之後各輪排的。騎士明確指定的加油地點或其他加油約束必須保留，不得取消或違反。

做法：加油停留的來源（`origin`）分成系統安排的（`planner`、`replan`）與騎士指定的（`free_text`、`clarification`）。重新規劃不得移除或搬移來源是 `free_text` 或 `clarification` 的加油停留。

測試：Q3-T32 重新規劃之後，騎士指定的加油停留都還在，檢查點不變；系統安排的可以被移除或更換。

### 9.8 C4：行程型態與休息方向（批准）

行程型態和休息方向放在同一輪追問，不增加第二輪。方向的問題依行程型態決定：來回行程、而且那個途經點在去程與回程各經過一次時，才要求選去程或回程；單向行程不需要選。行程型態本身也在這一輪問的時候，方向的問題標明「選擇來回時才需要回答」，主程式依回覆的行程型態決定用不用它。

測試：Q3-T33 行程型態未知、又有途經點的休息：同一次追問同時有行程型態與方向兩題；回覆單向時方向的答案不使用，回覆來回時依方向對應檢查點；沒有第二次追問。

### 9.9 C5：嚴格模式（批准）

嚴格模式下，凍結清單沒有對應的 `request_key` 或 `snapshot_id` 時停止；檔案的雜湊或 `freeway_check_method` 不符時也停止。都不回退到一般的快照。

測試：Q3-T34 凍結清單沒有這個請求的項目時停止，沒有採用任何其他快照。

### 9.10 附帶的兩件事

**快照的取得時間。** 「代號不含 `fetched_at`、內容相同就沿用舊檔」的設計保留。超過 30 天後可能重複向路線引擎查詢，是 MVP 的已知限制。不得偽造或覆寫取得時間；不為此新增複雜的快取架構。

**Profile 更新後的路線。** Profile 更新後，既有的路線必須依新的門檻重新分類；無法重建時，不可混用舊的類別與新的配速。這記錄為 `routes` 整合的驗收條件，**不擴張 BATCH-1 的 #10**：

| 編號 | `routes` 整合的驗收條件 |
| --- | --- |
| RI-1 | 路線目錄的 `category_scheme` 和所用配速表的 `category_scheme` 不同時，不計算 ETA |
| RI-2 | 這時由路線的幾何（路線快照或目標 GPX）依新的門檻重新分類路段，重建路線目錄的紀錄後再計算 |
| RI-3 | 幾何取不到、無法重建時回報錯誤，不產生計畫；不得以舊的類別搭配新的配速 |
