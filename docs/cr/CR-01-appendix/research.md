## 0. 結論先講

1. **現行 MVP 與 Proposal 最大的落差是「路線怎麼來」與「來回」**，不是 Agent 數量或分位數模型。Proposal 的問題定義、範例、規則 1 與 E2 指標全部以「起訖點／途經點 → 實際道路 → 當天來回、天黑前回到家」為前提（§1.3 p.6、§4.1 p.24、§4.8 p.32、§4.9 p.33）；現行 MVP 改成兩條約 47 公里的固定單向路段（DESIGN §2.1 FR1、G1 Q1）。
2. **既有程式大部分可以沿用。** 配速表是依曲率分類、與道路無關的；`build_route` 吃的是「一條路徑」。我用公開地標實測：Valhalla 回傳的幾何不經修改就能丟進 `build_route`（55 公里 → 54 段）[查證]。要改的是資料契約的幾個欄位、檢查點的產生方式，以及缺類別時整條路線變 UNKNOWN 的行為。
3. **Routing 的最小可行做法是 Valhalla 的 `motorcycle` costing 加上 `exclude_highways`。** 實測：預設值會走國道 1 號 149 公里（機車違法）；加上 `exclude_highways` 後改走台 61／台 64（大型重機可走的快速公路）[查證]。OSRM 公開伺服器不支援 `exclude=motorway`，會直接上國道 [查證]。Google Routes API 的條款不允許預先擷取與儲存內容，和「可重現的快照」衝突 [查證]。
4. **來回行程會暴露一個現行方法沒處理的誤差來源**：配速只算移動時間，路段只依曲率分類。從家裡騎到山區的平面轉場段（紅燈、市區、快速公路混在同一類）會讓回程時間偏樂觀。這是恢復 Proposal 情境時研究上必須處理的事 [推論，未用資料驗證]。

## 4. 使用情境 A–E

### A. 起點、終點、途經點 → 實際道路路線 → 規劃

- **Proposal 依據**：§1.3 p.6 問題定義；§4.1 p.24 正式定義；§4.4 ② p.26；§4.8 Alg.1 第 03 行 p.32。**屬於原始承諾。**
- **現有程式可做**：`build_route(route_id, name, path, …)` 把任何路徑切段、分類（[查證] 以 Valhalla 幾何實測可用，`TrackPoint.time` 給假值即可，函式不讀時間）；`compute_eta` 對任何路線運作；配速表與道路無關。
- **缺少**：地名 → 座標；座標 → 道路路徑（routing）；路線快照；沿線檢查點（加油站、途經點）的自動定位；路段 → 鄉鎮（查預報用）；契約欄位（`source_trip_id` 必填且須為 `T\d{3}`、`route_id` 限 `R\d{2}`）；輸入介面。
- **最小設計**：輸入起點、終點、0–5 個途經點（地名）→ 地名解析出候選、騎士確認 → Valhalla `motorcycle`＋`exclude_highways` → 幾何存成路線快照 → `build_route` → 沿線投影加油站成檢查點 → `compute_eta` → 既有的規則流程。
- **分類**：產品必要；研究必要（E2 的題目才不會只是兩條路）。Proposal 依據明確。

### B. 只給目的地或公路名稱；必要時追問，再建立路線

- **Proposal 依據**：§4.4.2 ③-1、TALK p.27；§4.7 流程圖「資訊足夠？→ 追問」p.31；§4.9 第 2 步「從哪一端進南橫？」p.33。**屬於原始承諾**（Proposal 自己的範例就是公路名稱）。
- **現有程式可做**：無。Smoke Test 的假工具 `find_route(query)` 已有「以文字找路線」的介面雛形（`experiments\llm_smoke_test\smoke_test.py`）。
- **缺少**：缺項判斷（起點、來回或單向、進出方向）；公路名稱 → 可路由的錨點。[查證] Nominatim 對公路名稱不可用：`台14甲線` 0 筆；`南橫公路` 回傳台南玉井、南化的平地片段；`阿里山公路` 回傳嘉義市的吳鳳南路。地名（`武嶺`、`梅山口`）可用。
- **最小設計**：一份人工整理的**公路與地標詞彙表**（10–20 條常見山路：名稱、別名、兩端入口錨點、必要的中途錨點、出處），同時充當 ⑥ Domain Knowledge 的內容。Planner 呼叫 `resolve_road` 或 `resolve_place`；有多個入口或缺起點時回傳追問。起點預設取 Rider Profile 的「出發錨點」（見 §5.5 隱私）。
- **分類**：追問缺項＝產品必要（Proposal）。詞彙表＝產品必要（小）。詞彙表以外的任意公路名稱自動解析＝可做非必要。

### C. 騎士提供目標路線 GPX

- **Proposal 依據**：**新需求**。與 §4.1「路線（或途經點）」相容，但 Proposal 的 GPX 匯入只用於配速（流程圖 p.31、Alg.2 p.32）。
- **現有程式可做**：`build_route` 直接可用；`align_to_route` 可檢查這條路以前騎過多少。
- **缺少**：`read_gpx` 只讀 `<trkpt>` 且**丟掉沒有時間的點**（`ingest\gpx.py` 第 21–24 行）；路線規劃 App 匯出的 GPX 常沒有時間，或用 `<rtept>`。需要一個只讀幾何的讀取函式。點很稀疏的 `<rte>` 應當成途經點走情境 A。不需要 map-matching。
- **最小設計**：幾何讀取 → 以 `resample_m` 重取樣 → `build_route`；路線來源標為 `target_gpx`。這條路徑同時是**沒有網路、沒有 routing 時的保底**，也讓 E2 的真實行程題可以直接用保留行程的幾何（§9）。
- **分類**：產品價值（選用輸入）；對研究有用但非必要。約 0.5 人日。

### D. 當天來回，天黑前回到起點

- **Proposal 依據**：Abstract p.4；§1.3 p.6；§4.1 p.24（最晚回到家、最晚回程時間）；規則 1 p.29；§4.9 p.33；E2 的「回程時間誤差」p.34。**這是 Proposal 最核心的情境。**
- **現有程式可做**：把來回當成一條路線（去程＋回程的路徑）即可，契約不衝突：路線本來就有方向；同一加油站在去回程各是一個檢查點（契約允許同位置多個檢查點）；折返點的停留用 `breaks` 表示（契約 4 允許在中間檢查點排休息）。規則 1 用終點（＝起點）的 `ETA_safe`，邏輯不變。規則 3 的「最後 20% 距離」在來回行程上反而更合理。
- **缺少**：來回路徑的組法（去回同路＝去程幾何反轉；環線＝途經點清單以起點收尾）；用語（「最晚回到起點時間」）；折返點停留時間的輸入；較長行程的油量與加油站（原本兩條短路線幾乎用不到）。
- **研究上的影響**：6–10 小時的來回行程自然會碰到日照限制，不必再刻意設計傍晚出發（G1 Q10）。但轉場段的時間估計變成主要誤差來源（§6.4）。
- **分類**：產品必要；研究必要。Proposal 依據最強。

### E. 個人資料稀少，或要規劃沒騎過的路

- **Proposal 依據**：部分。§1.6 p.8「任何匯入自己 GPX 的騎士都能各自訓練」；§4.5 p.28 以特徵預測，本來就意在推廣到沒騎過的路。**「資料不足時怎麼判斷、怎麼告知」是新需求**（對 NFR4 的延伸）。
- **現有程式可做**：依曲率類別的配速表可套到任何路；`min_segments`（Spike 用 30）擋掉樣本太少的類別；`align_to_route` 能算一條路被某趟行程涵蓋的比例。
- **缺少**：缺任一類別時 `compute_eta` 讓**整條路線**變 `unknown`（契約 4 不變條件 7）——在任意路線上太脆弱；沒有「這條路沒騎過」的偵測；沒有資料充足程度的分級與說法。設計見 §6。
- **分類**：涵蓋度報告與誠實告知＝產品必要＋研究必要（否則 E2 的時間誤差無法解讀）。零 GPX 的冷啟動＝可做非必要、新需求。

### 「依模糊偏好探索台灣最好的山路」

- **Proposal 依據**：無，**新需求**。§1.4 p.6 把彎道路線規劃歸給 Calimoto、Kurviger，並以「時間與風險整合」作為本專題的區隔。
- **評估**：有了公路詞彙表與 routing 之後，技術上可以做成「從詞彙表的 N 條路依偏好與距離挑 2–3 條，各自跑可行性驗證再比較」。Valhalla 另有 `use_curvature` 偏好參數 [查證文件]。但「最好」沒有客觀資料可以佐證，容易做出無法驗證的宣稱，也會稀釋核心研究問題。
- **分類**：可做非必要（Stretch）。若要做，限定為「在知識庫已收錄的路線中依可行性篩選」，不宣稱最佳。

### 5.5 殘餘的 routing 風險

- `exclude_highways` 在文件上標為 EXPERIMENTAL，並註明可能找不到路徑。我只測了一組起訖。
- 個別快速公路或市區高架另有禁行機車的公告（條文但書），OSM 只在 73 條 trunk way 標了 `motorcycle=no`。路線可能包含實際上禁行的路段 → 結果要列出主要道路名稱供騎士檢視，並固定加一句路權需自行確認。
- **由 OSM 幾何算出的曲率，和由 1 Hz GPS 軌跡算出的曲率是否落在同一類別，尚未驗證**（需要拿騎過的路段對照，會用到私有資料，我沒有做）。這是 routing 採用前必須先做的第一個 Spike：若有系統性偏差，分級門檻要分開校正。
- 住家座標送到第三方伺服器是隱私外洩。自架可完全避免；用公開服務時一律用出發錨點。

## 6. 資料流程：歷史 GPX → 個人 Profile → 目標路線

### 6.1 流程

```text
歷史 GPX（多檔）─ ingest ─▶ 衍生路段表（私有／公開）─ pace ─▶ 個人配速表（含各類別的資料充足程度）
                    │                                              │
                    └─ 裁切後軌跡（私有）─▶ 「騎過的路」索引        │
目標路線 ◀─ routing 結果（情境 A、B、D）或 目標 GPX（情境 C）       │
   └─ build_route ─▶ 路段＋類別 ─▶ 沿線檢查點 ─▶ compute_eta ◀──────┘
                         └─ 與「騎過的路」比對 ─▶ 這條路的熟悉程度
```

### 6.2 多檔匯入與 Profile 更新（現況的缺口）

| 項目 | 現況 [查證：`ingest\__main__.py`] | 最小修改 |
| --- | --- | --- |
| 多檔 | `--gpx-dir` 一次處理資料夾內全部 `*.gpx` | 可沿用 |
| 更新 | 已有 `trip_manifest.json` 時直接沿用舊清單，**資料夾裡新增的 GPX 不會被匯入**；`trip_id` 依檔名排序編號 | 清單改為合併：新檔接續編號、以內容雜湊去重複、保留既有 `trip_id` |
| 角色 | `trip_role` 由 Spike 腳本依示範路線指定 | 改成與路線無關的規則，例如日期最新的 K 趟為 `holdout`（對應 Proposal「以最新行程做時間外推」p.7） |
| 重建 | 重新執行即重建配速表，版本以 `pace_version` 標示 | 沿用；每次重建輸出涵蓋度報告 |
| 介面 | 指令 | `st.file_uploader` 多檔上傳是小工作；研究上指令即足夠 |

分類：清單合併與重建＝產品必要（Proposal §4.4 ②、Alg.2）。介面上傳＝產品價值（小）。

### 6.3 不設「至少 5 檔」的硬門檻：改判斷資料品質與類別涵蓋

| 層級 | 指標（都能由現有欄位算出） | 用途 |
| --- | --- | --- |
| 單趟 | 裁切後長度、`quality` 為 ok／suspect／invalid 的路段數、GPS 跳點數（`TripReport` 已有） | 這趟能不能用；不能用時說明原因，不計入 |
| 每個類別 | ok 路段數、貢獻的行程數、累計公里、速度的四分位距 | 該類別配速的資料充足程度 |
| 目標路線 | 各充足程度所占的里程比例；與歷史軌跡重疊的里程比例（`align_to_route` 對所有行程取聯集） | 這次估計有多可信 |

建議的三級（門檻是暫行值，須在正式 E1 之前只用配速行程定案；可用 E1 的「行程數對誤差」曲線佐證）：

| 級別 | 暫行條件 | ETA 的處理 | 對規則 1 的影響 |
| --- | --- | --- | --- |
| 充足 | 該類別 ≥30 段且來自 ≥3 趟 | 用類別配速 | 正常判定 |
| 有限 | 10–29 段，或只來自 1–2 趟 | 用類別配速，標示「樣本有限」 | 正常判定，結果加註 |
| 不足 | <10 段 | **不沿用其他類別**；改用整體個人中位數並明確標示為較粗的估計 | 路線里程中「不足」的比例超過門檻時，規則 1 為 UNKNOWN（計畫最多 CONDITIONAL），原因「個人配速依據不足」 |

這需要改契約 4 不變條件 7（缺一個類別就整條 `unknown`）：改為逐路段記錄估計依據（`pace_basis`），仍然不靜默補值（NFR4）。

系統在各情況要說的話（由固定模板產生，不由 LLM 自由發揮）：

| 情況 | 說法（示意） |
| --- | --- |
| 涵蓋充足、路也騎過 | 「這條路線有 X% 的里程你以前騎過；估計依據是你在同類彎道的 N 段紀錄。」 |
| 路沒騎過、類別充足 | 「**這條路你沒有騎過。**時間是用你在彎曲程度相近的路段的配速估的，實際路況（坡度、路面、車流）沒有納入。」 |
| 類別有限或不足 | 「你的紀錄中高曲率路段只有 N 段（來自 M 趟），這部分的時間估計不可靠；保守估計沒有覆蓋率保證。多匯入幾趟山路行程可以改善。」 |
| 沒有任何可用 GPX | 不產生個人化估計。是否改用導航引擎的時間並標為非個人化，屬新需求（Stretch） |

分類：涵蓋度指標與說法＝產品必要＋研究必要；Proposal 只有間接依據（§1.6 p.8），告知機制是新需求。

### 6.4 來回行程帶出的配速適用性問題

- 現行分類只看曲率，DESIGN R16 已記錄「分不出快速道路與一般直路」。固定山路段時影響小；從家裡出發的來回行程，C1 會同時包含快速公路、省道平面段與市區。
- ETA 只算移動時間（`moving_time_s`），紅燈與塞車的停等不在內。衍生路段表其實有 `stopped_time_s`，但混著加油、吃飯的長停留。
- [推論] 兩者都會讓長距離轉場的時間偏樂觀，直接影響規則 1 與「回程時間誤差」。**沒有用資料驗證過。**

| 做法 | 內容 | 成本 | 分類 |
| --- | --- | --- | --- |
| a. 先量再決定 | E1 改成評估**整趟**（不只示範路段），看誤差是否集中在 C1 與有停等的行程 | 併入 E1 | 研究必要 |
| b. 停等寬放 | 由自己的行程估「短停留」（例如單次 <3 分鐘）占移動時間的比例，按類別加到典型時間 | 約 0.5–1 人日；配速方法要記入 Change Log | 研究必要（若 a 顯示有偏差） |
| c. 道路等級 | 以自架 Valhalla 的 `trace_attributes` 替歷史路段補 `road_class`，分類改為曲率×道路等級 | 約 1.5–2 人日；需自架（會送出軌跡） | 可做非必要；Proposal §4.5 的道路等級特徵 |
